# Voice-First Prompting / พา agent เข้าใจโจทย์ด้วยการพูดยาว

**Voice-first prompting** คือการใช้เสียงเป็นวิธีป้อนโจทย์ให้ agent โดยพูดต่อเนื่องเป็นสิบ ๆ นาทีแบบคิดออกมาดัง ๆ แล้วให้ระบบถอดเสียงและทำความสะอาดก่อนส่งเข้า agent ต่างจากการใช้ dictation สั่งงานสั้น ๆ [[lex-fridman|Lex Fridman]] อธิบาย workflow นี้ให้ [[dhh|DHH]] ฟังใน [[dhh-strategies-programming-with-ai-agents-lex-clips|คลิปเรื่องวิธีทำงานกับ agent]]

## สองแบบที่ไม่เหมือนกันเลย

คนมักเหมารวมว่า "ใช้เสียงคุยกับ AI" เป็นเรื่องเดียว แต่ในคลิปนี้มีสองแบบที่ใช้กับงานคนละชนิด

| แบบ | ความยาว | ใช้กับ | ความผิดพลาดสำคัญไหม |
|---|---|---|---|
| dictation สั่งงาน | ไม่กี่ประโยค | สั่งคำสั่ง, แก้ข้อความ | สำคัญมาก เพราะข้อความคือผลลัพธ์ |
| พูดยาวเพื่อวางโจทย์ | 10–20 นาที ถึงเป็นชั่วโมง | design ช่วงต้น, พาเข้าใจโจทย์ | สำคัญน้อยกว่า เพราะ agent อ่านความหมายรวม |

DHH อยู่ฝั่งซ้ายและใช้น้อย เขาบอกว่า [[omarchy|Omarchy]] มี [[voxtype|VoxType]] ให้กดค้าง F9 แล้วพูด ใช้กับคำสั่งสั้นได้ดี แต่ตัวเขาไม่ได้คิดด้วยการพูด ชอบพูดตอนอยู่ในรถ พอมานั่งหน้าคีย์บอร์ดก็อยากพิมพ์ Lex อยู่ฝั่งขวาและใช้เป็นหลัก

**ได้อะไร:** ก่อนจะสรุปว่าเสียงเวิร์กหรือไม่ ต้องดูก่อนว่าใช้กับงานแบบไหน DHH เองบอกว่าเขาอาจใช้ผิดแบบมาตลอด เพราะลองแค่พูดสองประโยคแล้วรู้สึกว่าพิมพ์เร็วกว่า

## ทำไมพูดยาวได้เปรียบ

จุดที่ Lex ชี้คือ prompt แบบนี้ไม่ตีกรอบเกินไป

> "It doesn't have the problem of over specification. Because of how much stream of consciousness thinking the system has about what you're imagining."

เวลาพูดยาว สิ่งที่ติดไปด้วยคือทางที่คิด รวมทั้งช่วงที่เปลี่ยนใจกลางทางเรื่อง design เขาบอกว่าปล่อยให้อยู่ในนั้นเลย agent จึงได้เห็นทั้งข้อสรุปและเหตุผลรอบ ๆ ไม่ใช่แค่ข้อกำหนดที่ถูกเกลาจนแข็ง

ตรงนี้สวนสัญชาตญาณของสาย [[spec-driven-development|spec-driven development]] อยู่บ้าง คือ spec ที่เขียนแน่นเกินไปตอนที่ยังไม่รู้คำตอบ จะล็อกทางเลือกเร็วเกินไป การพูดยาวเก็บความไม่แน่ใจไว้ในรูปที่ agent อ่านได้ ใกล้กับที่ [[plan-mode-as-prompting|plan mode]] ทำ คือคุยให้จบก่อนแล้วค่อยลงมือ

**ผลคือ:** เสียงเหมาะกับช่วงต้นของงานที่โจทย์ยังไม่คม Lex บอกว่าถ้าจะสร้าง Omarchy ใหม่จากศูนย์ เขาจะเริ่มด้วยการพูดชั่วโมงหนึ่ง

## pipeline สองชั้นที่ต้องมี

เสียงดิบใช้ตรง ๆ ไม่พอ เพราะพูดถึงชื่อไฟล์ ชื่อ function และคำเฉพาะเยอะ Lex ทำสองชั้น

1. **ถอดเสียง** เขาใช้ [[elevenlabs|ElevenLabs]] และบอกว่าเป็น speech-to-text ที่ดีที่สุดที่เขาลอง
2. **ทำความสะอาด transcript ด้วย LLM** โดยให้ dictionary คำเฉพาะของเขา และมี agent ที่ไปกวาด code base เพื่อดึงคำที่เขาใช้บ่อยมาเป็นรายการอ้างอิง เวลาคุยเรื่องข้อความก็ให้รู้จักชื่อคนใน Gmail กับ WhatsApp ด้วย

ชั้นที่สองคือหัวใจ มันคือการทำ [[keyword-biasing|keyword biasing]] หรือการเอียง model ให้เขียนคำเฉพาะถูก แต่ทำหลังการถอดเสียง ไม่ใช่ตอนถอด ข้อดีคือใช้กับ ASR ตัวไหนก็ได้และแก้ dictionary ได้ทันที ข้อเสียคือยังพลาดได้เมื่อคำที่ถอดผิดกลายเป็นคำอื่นที่ฟังดูเข้าท่าพอจนไม่มีอะไรสะกิดให้แก้

**ได้อะไร:** งานหนักไม่ได้อยู่ที่การเลือก model ถอดเสียง แต่อยู่ที่ชั้น post-processing ที่รู้จักศัพท์ของเราและ code base ของเรา ดู [[automatic-speech-recognition|ASR]] และ [[word-error-rate|WER]]

## ยอมช้าได้แค่ไหน

Lex บอกว่าเขายอมรอ 5–10 วินาทีให้ pipeline ทำงานให้เสร็จ ไม่จำเป็นต้อง real time DHH เห็นด้วยแล้วขยายเป็นหลักการว่า

> "Don't let the perfect be the enemy of good."

เขายก iPhone รุ่นแรกที่เน็ตช้ามากและเครื่องอ่อน แต่คนก็ยังใช้เพราะไม่มีของอื่นแทน เกณฑ์ที่เขาเสนอคือถ้าแก้ปัญหาที่คนยังไม่มีทางแก้ คนยอมรอ ถ้าเข้าตลาดที่มีของอยู่แล้ว ความช้ากลายเป็นข้อเสียทันที

ที่น่าสังเกตคือ ตรงนี้เป็นเหตุผลว่าทำไมชั้น post-processing คุ้ม การรอสิบวินาทีเพื่อได้ transcript ที่สะกดชื่อ function ถูก ดีกว่าได้ transcript ทันทีแล้วต้องนั่งแก้เอง

## ข้อจำกัด

ทั้งหมดนี้เป็น workflow ของคนสองคนที่เล่าให้ฟัง ไม่มีตัวเลขวัด ไม่รู้ว่า transcript ยาวสิบห้านาทีเมื่อกลายเป็น prompt แล้วกิน context เท่าไร และคลิปไม่ได้พูดถึงว่า agent จับใจความจาก stream of consciousness ที่มีการเปลี่ยนใจกลางทางได้แม่นแค่ไหน หรือเสี่ยงหยิบไอเดียที่ผู้พูดทิ้งไปแล้วมาทำหรือเปล่า ดู [[context-rot|Context Rot]] และ [[dumb-zone|Dumb Zone]] ประกอบ

อีกข้อคือคนคิดไม่เหมือนกัน DHH เป็นคนพิมพ์ Lex เป็นคนพูด สองคนเปิดเผยเองว่าเป็น introvert ทั้งคู่ ดังนั้นเรื่องนี้ไม่ใช่เรื่องบุคลิกอย่างเดียว แต่เป็นเรื่องว่าความคิดของใครไหลออกมาทางไหนได้ดีกว่า
