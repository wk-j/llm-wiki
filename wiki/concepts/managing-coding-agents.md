# Managing Coding Agents / มอบหมายและตรวจงานจาก coding agent

เวลาให้ agent เขียนโค้ด เรามักไม่ได้ลงมือเขียนเองทุกบรรทัด แต่ยังต้องเลือกงาน อธิบายว่าต้องการอะไร ตรวจผล และตัดสินใจว่าจะนำไปใช้หรือไม่ [[addy-osmani|Addy Osmani]] ผู้เขียนเรื่องการพัฒนาซอฟต์แวร์และ AI เปรียบงานเหล่านี้กับทักษะผู้จัดการใน [[your-coding-agents-made-you-a-manager-osmani|Your Coding Agents Made You a Manager]]

จุดสำคัญคือให้ agent ทำงานและตรวจข้อผิดพลาดพื้นฐานเองได้ แล้วใช้เวลาของคนกับเรื่องที่ต้องเข้าใจผู้ใช้ รับผิดชอบความเสี่ยง หรือตัดสินใจเลือกทาง

## ก่อนมอบหมาย บอกผลที่ต้องการและวิธีตรวจให้ครบ

คำขอที่ดีช่วยให้ agent ไม่ต้องเดาว่าเราจะพอใจงานแบบไหน ควรบอก:

- **อยากได้ผลอะไร และทำไปทำไม:** เช่น แก้หน้าเว็บที่ลูกค้าแจ้งว่าโหลดช้า พร้อมระบุเกณฑ์เวลาที่ต้องการ
- **ห้ามเปลี่ยนอะไร และยังไม่ต้องทำอะไร:** เช่น คงรูปแบบ API เดิม และยังไม่แก้หน้าตา UI
- **ตรวจด้วยอะไร:** ระบุคำสั่ง test สคริปต์วัดผล หรือขั้นตอนลองใช้
- **ส่งหลักฐานอะไรกลับมา:** diff ที่แก้ ผล test และค่าก่อนกับหลัง

ไม่จำเป็นต้องอธิบายสิ่งที่ agent เปิด repo อ่านเองได้หมด ให้เน้นเหตุผลและข้อจำกัดที่ไม่อยู่ในโค้ด ถ้ายังไม่ชัด ให้มันช่วยถามและเขียน spec ก่อนเริ่มงาน

## ระหว่างทำ ตรวจแผนและหยุดเมื่อเข้าใจผิด

อ่านแผนก่อนให้แก้งานใหญ่ โดยดูว่ามันกำลังตั้งสมมติฐานแทนเราหรือไม่ ถ้าใช้หลาย agent ต้องแยกงานไม่ให้แก้เรื่องเดียวกันซ้ำ และตกลง interface ที่ใช้ร่วมกันก่อน [[git-worktrees|การแยก checkout ด้วย worktree]] ช่วยแยกไฟล์ที่ทำงาน แต่ไม่ได้แก้ข้อขัดแย้งในการออกแบบแทนคน

เมื่อเห็นว่า agent เข้าใจผิด ให้แก้ทันที Addy เสนอว่าถ้าแก้สองครั้งแล้วยังไม่ตรง ให้เริ่ม session ใหม่ด้วยคำขอที่ชัดขึ้น แทนการต่อบทสนทนาที่เต็มไปด้วยวิธีที่ลองแล้วไม่สำเร็จ

ถ้าต้องเตือนเรื่องเดิมซ้ำหลายงาน ให้จดไว้ในคำแนะนำของทีม หรือทำเป็นเครื่องมือตรวจ ดู [[harness-ratchet|การปรับระบบจากข้อผิดพลาดที่เคยเกิด]] กฎที่ต้องบังคับจริงจึงค่อยใช้ hook หรือ permission ควบคุม ส่วนความชอบทั่วไปไม่ต้องกลายเป็นข้อห้ามทุกข้อ

## ก่อนรับงาน อย่าอ่านแค่คำว่าเสร็จหรือ test ผ่าน

ให้ agent รันตรวจเองและแสดงผลก่อน แล้วอ่าน diff ในส่วนที่มีผลต่อพฤติกรรมผู้ใช้ ความปลอดภัย หรือข้อกำหนดสำคัญ จะให้ agent อีกตัวที่ไม่ได้ร่วมเขียนมาตรวจซ้ำก็ได้ ดู [[agentic-code-review|การตรวจโค้ดที่ agent สร้าง]]

Test ผ่านบอกได้เฉพาะสิ่งที่ test ตรวจ ฟีเจอร์ที่ผ่านทุก test ยังอาจไม่ตอบโจทย์หรือทำให้ผู้ใช้ใช้งานยากขึ้น คนจึงยังต้องตัดสินใจว่าจะนำงานนั้นไปใช้หรือไม่ และควรแบ่ง diff ให้เล็กพออ่านเข้าใจ

นี่คือเหตุผลที่ต้องระวัง [[cognitive-surrender|การเชื่อตาม AI โดยไม่ตรวจเอง]] ตามที่ Addy อธิบายใน [[critical-thinking-when-agents-do-the-work-osmani|บทความเรื่องการคิดอย่างรอบคอบเมื่อ agent ทำงานแทน]]

## ถ้าจะปล่อยทำงานเอง ต้องมีเงื่อนไขหยุดที่ชัดเจน

ก่อนปล่อย [[long-running-agents|agent ทำงานต่อเนื่อง]] โดยไม่มีคนเฝ้า ให้กำหนดห้าเรื่อง: งานเสร็จเมื่อไร ตรวจอย่างไร แก้ไฟล์หรือใช้เครื่องมืออะไรได้บ้าง ใช้เวลาหรืองบเท่าไร และเมื่อไรต้องหยุดรอคนอนุมัติ

เริ่มลองกับงานจำนวนน้อยก่อน เช่น สามไฟล์ แล้วค่อยขยายเมื่อเห็นว่ามันทำตามเป้าและหยุดถูกจุด หลักนี้เชื่อมกับ [[loop-engineering|การออกแบบขั้นตอนทำงานและตรวจซ้ำ]] คนไม่ต้องตามทุกการเรียก tool แต่ยังควบคุมสิ่งที่อาจสร้างผลเสียได้

## เปิดเพิ่มเท่าที่ตรวจงานได้ทัน

ถ้าเปิด agent เพิ่มแล้วต้องนั่งตามทุกตัว งานตรวจจะกองจนอ่านไม่ไหว ปัญหานี้เรียกว่า [[orchestration-tax|ภาระติดตามและประสานงานจากหลาย agent]] ควรให้ระบบรันตรวจและแจ้งเฉพาะผลที่ต้องดู ก่อนเพิ่มจำนวนงานพร้อมกัน

วัดทั้งเวลาที่ใช้ปิด PR และจำนวนครั้งที่ต้อง revert หรือแก้ใหม่ จำนวนบรรทัดที่ AI เขียนไม่ได้บอกว่าผู้ใช้ได้ประโยชน์แค่ไหน ก่อนเริ่มงานใหม่จึงยังต้องถามว่าใครต้องการ และคุ้มกับภาระดูแลต่อหรือไม่

## อย่าใช้ agent เป็นเหตุให้ละเลยทีมคน

การควบคุมหลาย session ไม่ได้ฝึกเรื่องแรงจูงใจ ความขัดแย้ง หรือการพัฒนาคน ถ้า agent รับงานพื้นฐานไปหมด ก็ต้องหาโอกาสให้ junior developer ได้ฝึก และยังต้องเผื่อเวลาคุยกับเพื่อนร่วมทีม

ข้อแนะนำในหน้านี้เป็นการสังเคราะห์แนวทางทำงานจากบทความ ไม่ใช่ผลทดลองว่าทำตามแล้วจะเพิ่มผลผลิตได้เท่าใด
