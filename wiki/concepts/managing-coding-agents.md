# Managing Coding Agents / การจัดการ coding agent

แนวคิดจาก [[addy-osmani|Addy Osmani]] ใน [[your-coding-agents-made-you-a-manager-osmani]] คือ ถ้าเราใช้ coding agent ทั้งวัน เราก็กำลังจัดการอยู่แล้ว แม้จะไม่ได้มีตำแหน่งผู้จัดการ การจัดการในความหมายนี้ไม่ใช่การจมอยู่ในปฏิทิน แต่เป็นการทำให้ผลงานดีขึ้นด้วยการเปิดทางให้งานเดินได้ ได้แก่ เลือกงาน เขียนคำสั่ง มอบหมาย ติดตาม ประเมินของที่ได้ และตัดสินว่าอะไรจะออก

คนที่ได้ผลดีจาก agent ไม่จำเป็นต้องเก่ง prompt ที่สุด แต่เป็นคนที่เรียนรู้การจัดการ ไม่ว่าจะตั้งใจฝึกหรือไม่ ข้อบ่นเรื่องผู้จัดการแย่ เช่น ส่งงานคลุมเครือ ขาดบริบท หรือเป้าเลื่อนไปเรื่อย ๆ ก็ใช้เป็น bug report สำหรับวิธีคุยกับ agent ได้

บทความนี้ไม่ได้บอกว่า agent มาแทนผู้จัดการหรือเพื่อนร่วมงาน

## นิสัยที่ได้ผล

- ให้ agent มีตัวตรวจเอง เช่น test, การ build, linter หรือภาพหน้าจอ แล้วขอหลักฐาน อย่าเป็นชุด test ของมันเอง [[agentic-code-review]]
- ใส่บริบทที่ repo พูดแทนไม่ได้ เช่น เป้า เหตุผล ข้อจำกัด สิ่งที่อยู่นอกงาน และเกณฑ์ว่าเสร็จเมื่อไร แล้วปล่อยให้มันเลือกวิธีเอง แนวนี้เรียกว่า context, not control หรือ commander's intent
- แก้ซ้ำเกินหนึ่งครั้งแล้ว ให้จดใน `CLAUDE.md` หรือทำเป็น skill ที่ใช้ด้วยกันได้ แล้วคอยดูว่า model ใหม่ยังต้องการคำแก้พวกนี้ไหม แนวนี้ใกล้ [[harness-ratchet]]
- ให้มันตัดสินใจเองเป็นปกติ แล้วบังคับด้วย hook หรือ deny rule เฉพาะเรื่องที่งอไม่ได้ อย่าจุกจิกด้วยกฎที่แค่ความชอบ หรือนิสัยของ model เก่า
- ตกลงแผนก่อนให้สร้าง อ่านสมมติฐานที่ซ่อนอยู่ แล้วแยกงานขนานไม่ให้ทับกัน เช่น ใช้ `/batch` กับ [[git-worktrees]]
- ดึงทางตั้งแต่ต้น ถ้าแก้สองครั้งแล้วยังไม่เข้าที่ ให้เริ่มเซสชันใหม่ด้วย prompt ที่ดีขึ้น หรือใช้ `/rewind` แล้วนำบทเรียนไปเขียนต่อ
- มอบหมายงาน แต่อย่ามอบหมายการตัดสินใจ ความถูกต้องของสินค้า ความปลอดภัย และอะไรจะออก ยังเป็นของคน การอนุมัติ diff ใหญ่เพียงเพราะ test เขียวคือการรับรองโค้ด ไม่ใช่ review
- ออกแบบรอบที่ไม่มีคนเฝ้าด้วยคำถามว่าเสร็จเมื่อไร ตรวจเองได้อย่างไร ขอบเขตอยู่ที่ไหน ราวกั้นคืออะไร และใครอนุมัติจุดที่ย้อนไม่ได้ แนวนี้ใกล้ [[loop-engineering]] และ [[long-running-agents]]
- ขยายการตรวจ ไม่ใช่ขยายความใส่ใจ นี่คืออีกหน้าของ [[orchestration-tax]] วัดคุณภาพด้วย เช่น เวลาที่ PR ใช้จนจบ ความถี่ที่ต้อง revert อย่าวัดความสำเร็จจากร้อยละของโค้ดที่ AI เขียน
- ตัดสินใจว่าจะไม่สร้างอะไร เพราะของถูกสร้างยังต้องมีคน review ดูแลความปลอดภัย และดูแลระยะยาว

## จุดที่เปรียบกับผู้จัดการใช้ไม่ได้

การรัน agent หลายตัวไม่ได้แปลว่าพร้อมจัดการคน การย้อนงานเกือบฟรี จึงทดลองทางใหญ่ได้ง่ายกว่าการทำงานกับคน Agent ไม่มีประสบการณ์ มีแต่สมุดโน้ต จึงต้องเขียนบทเรียนให้ทั้งทีม มันเต็มใจและมั่นใจ จึงเผลอเชื่อมากเกินไป ซึ่งเชื่อมกับ [[cognitive-surrender]] ต้นแบบมีชุดเดียวและเปลี่ยนตาม model แต่ละรุ่น งานเริ่มต้นที่เคยฝึก junior ยังต้องมีรอบฝึกตั้งใจ และทีมคนยังสำคัญ อย่าให้การจัดการ agent แย่งเวลาสร้างทีม

staff engineer ที่ดีวางบริบท นิยามว่าเสร็จ และ review ให้คนรอบตัวทำงานได้ดีขึ้นมาตลอด Agent ทำให้วิศวกรทุกคนฝึกแบบนี้ได้เร็วขึ้น โดยยกเลิกความผิดพลาดของตัวเองได้ถูก
