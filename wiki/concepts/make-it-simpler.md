# Make It Simpler / คำสั่งที่คนยังต้องพูดเอง

**Make It Simpler** คือข้อสังเกตว่า agent เขียน code ให้ทำงานถูกได้แล้ว แต่ยังไม่ลดความซับซ้อนของ code ที่ตัวเองเขียนเอง จนคนต้องเป็นคนพูดว่า "ทำให้ง่ายกว่านี้" คำนี้มาจากที่ [[dhh|DHH]] ผู้สร้าง Ruby on Rails เล่าใน [[dhh-strategies-programming-with-ai-agents-lex-clips|บทสัมภาษณ์กับ Lex Fridman]]

## เรื่องเล่าจากหน้างาน

DHH เล่าว่ารูปแบบที่เจอซ้ำ ๆ คือ agent ทำงานเสร็จแล้วบอกว่าเสร็จ ส่ง agent อีกตัวมา review ตัว reviewer ก็บอกว่าผ่าน จนถึงตอนที่เขาอ่านแล้วทักสั้น ๆ ว่าดูซับซ้อนเกินไปหน่อย agent ตอบว่าใช่ ทำซับซ้อนเกินจริง แล้วตัดเหลือครึ่งเดียว

> "It blows my mind how often an agent can do something, say it's done, have the work reviewed by another agent, they say it's done, and then I go like, 'Ah, looks a little too complicated for me.'"

คำถามที่เขาถามต่อคือทำไมไม่ทำอย่างนั้นตั้งแต่แรก แล้วมีคนตอบเขาว่าคนก็เป็นแบบเดียวกัน เขียนงานเสร็จส่งให้คนอื่นดู อีกฝ่ายบอกว่ารู้สึกซับซ้อนไปนะ เราก็มักเห็นด้วยและตัดออกได้

ผลคือ ปัญหานี้ไม่ได้อยู่ที่ model ไม่รู้ว่าอะไรง่ายกว่า มันรู้ทันทีที่ถูกทัก แต่มันไม่ได้เริ่มจากตรงนั้นเอง

## ทำไม agent reviewer ไม่จับ

จุดที่คมที่สุดของเรื่องนี้คือ **reviewer ที่เป็น agent ก็ปล่อยผ่าน** [[adversarial-review-loops|Adversarial review loop]] ตั้ง reviewer ให้หาว่า code ผิดตรงไหน แล้วได้ผลดีกับ bug ที่ compile ผ่านและดู plausible แต่ "ซับซ้อนเกินจำเป็น" ไม่ใช่ความผิด มัน run ผ่าน test ผ่าน อ่านแล้วก็ดูสมเหตุสมผล reviewer ที่ถูกสั่งให้หาความผิดจึงไม่มีอะไรจะรายงาน

อีกชั้นคือ code ที่ป้องกันไว้เยอะ มี abstraction เผื่อ มี error handler ครบ มัก "ดูดี" ตามมาตรฐานที่ model เห็นมาใน training data ([[llm-coding-pitfalls|Overcomplication]] ในกับดักของ Karpathy) reviewer ที่ถือมาตรฐานเดียวกันเลยเห็นเป็นข้อดี ไม่ใช่ข้อเสีย

**ได้อะไร:** ถ้าอยากให้ระบบจับความซับซ้อนเกินได้ ต้องตั้งเป้าให้ reviewer ตรง ๆ ว่างานนี้คือหาว่าตัดอะไรได้ ไม่ใช่หาว่าอะไรพัง คลิปไม่ได้ทดลองแบบนั้น จึงยังเป็นข้อเสนอที่ต้องลอง ไม่ใช่ผลที่ยืนยันแล้ว

## คำสั่งที่เลิกต้องพูด กับคำสั่งที่เพิ่งต้องพูด

DHH เทียบกับยุคก่อนว่ามุกเก่าคือต้องบอก agent ว่า "อย่าทำผิด" ตอนนี้เขาบอกว่าไม่ต้องบอกแล้ว เพราะ harness รัน test อัตโนมัติและป้อนผลกลับให้ agent เอง

> "But you actually do have to tell them, 'Make it simpler.'"

เหตุผลที่ทั้งสองอย่างต่างกันอยู่ที่การวัด ความถูกต้องมี test เป็นตัวตัดสินแทนคนได้ ความเรียบง่ายไม่มีเครื่องวัดที่เชื่อได้ จำนวนบรรทัดกับ complexity metric บอกได้แค่บางส่วน สุดท้ายยังต้องมีคนอ่านแล้วรู้สึกว่ามันไม่สมส่วนกับปัญหา ดู [[verifiability|Verifiability]]

**ผลคือ:** งานที่ verify แบบอัตโนมัติได้ ย้ายไปอยู่ใน harness แล้ว งานที่เหลือให้คนคือส่วนที่วัดไม่ได้

## บทของคนคือ editor

DHH บอกว่าเขาไม่ต้องแกะสลักทุกบรรทัดเองแล้ว แต่ยังดู code อยู่ ดูรูปทรงและสัดส่วน เขาเปรียบว่าเหมือน Da Vinci ที่มีลูกศิษย์ทั้งสตูดิโอช่วยสกัดหินอยู่ ส่วนตัวเขาเดินมาบอกว่าสัดส่วนยังไม่ได้

> "I can tell you when the argument doesn't land. I can tell you when the shape isn't proportional to the problem."

คำว่า "สัดส่วนไม่สมกับปัญหา" ใช้งานได้จริงกว่าคำว่าซับซ้อน เพราะมันเทียบสองอย่าง คือขนาดของ code ที่ได้มา กับขนาดของโจทย์ที่ตั้งไว้ ปัญหาเล็กที่ได้ code ใหญ่คือสัญญาณ ไม่ต้องรู้ก่อนว่าจะตัดตรงไหน

ตรงนี้ต่อกับ [[taste-paradox|Taste Paradox]] โดยตรง ความรู้สึกว่าสัดส่วนเพี้ยนมาจากการเคยเขียนงานชนิดนั้นเองมาก่อน [[eh-gland|ต่อมเอ๊ะ]] ที่ทักได้ว่า "มันควรสั้นกว่านี้" ต้องมีของเทียบในหัว

**ได้อะไร:** feedback ที่สั้นที่สุดมักได้ผลมากที่สุด ไม่ต้องเขียน spec ใหม่ แค่ทักว่าซับซ้อนเกิน แล้วให้ agent เสนอรุ่นที่เล็กลง

## วิธีใช้จริง

- ทัก **หลัง** งานผ่าน test แล้ว ไม่ใช่ก่อน เพราะเป้าคือลดของที่ไม่จำเป็น ไม่ใช่ลดความพยายามให้ถูก
- ทักด้วยคำถามเทียบขนาด เช่น งานนี้ควรใช้กี่บรรทัด หรือถ้าตัด abstraction ออกหมดจะเหลืออะไร
- เขียนความชอบเชิง style ไว้ในไฟล์คำสั่งประจำ repo ([[claude-md]]) แต่อย่าคาดหวังว่าจะไม่ต้องเตือนซ้ำ DHH เองมีข้อห้ามเรื่อง early exit เขียนไว้ใน `AGENTS.md` แล้วยังต้องเตือนทุกครั้งที่จับได้
- อย่าใช้คำนี้เป็นข้ออ้างในการตัดสิ่งที่จำเป็นออก บาง precondition มีเหตุผล ถ้าตัดแล้วต้องมี test ยืนยันว่ายังถูก

## ข้อจำกัด

นี่เป็นประสบการณ์ของโปรแกรมเมอร์คนหนึ่งกับงาน bash และ Linux configuration ใน [[omarchy|Omarchy]] ไม่ใช่ผลทดลอง คำว่า "ตัดเหลือครึ่ง" เป็นการเล่า ไม่มีตัวเลขวัด และการที่ agent ยอมเห็นด้วยทันทีที่ถูกทักก็มีอีกด้าน คือมันอาจโอนอ่อนตามคนพูดโดยไม่ได้คิดใหม่จริง ๆ ถ้าคนทักผิด มันก็อาจตัดของที่ควรอยู่ออกด้วยความเต็มใจเท่ากัน
