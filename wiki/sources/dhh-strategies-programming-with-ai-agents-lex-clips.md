# Strategies for Programming with AI Agents / วิธีทำงานกับ agent ที่ DHH กับ Lex คุยกัน

คลิปนี้เป็นอีกช่วงของบทสัมภาษณ์เดียวกันกับ [[dhh-ai-programming-setup-lex-clips|คลิปเรื่องชุดเครื่องมือของ DHH]] แต่คุยคนละเรื่อง คลิปก่อนพูดถึงว่าเขาจัดเครื่องและ session อย่างไร คลิปนี้พูดถึง **วิธีสั่งงานและตรวจงาน agent** คือสั่งอะไร ดัดนิสัยอะไร แล้วคนยังต้องทำอะไรอยู่

[[dhh|David Heinemeier Hansson (DHH)]] ผู้สร้าง Ruby on Rails และ [[omarchy|Omarchy]] ซึ่งเป็น Linux distribution ของเขาเอง เล่ากับ [[lex-fridman|Lex Fridman]] ถึงสามเรื่องใหญ่ ๆ คือการรีดขนาดและความเร็วของ installer ด้วย agent, การที่ agent ยังชอบเขียนอะไรซับซ้อนเกินจนคนต้องบอกว่า "ทำให้ง่ายกว่านี้" และการสั่งงานด้วยเสียง ปิดท้ายด้วยภาพระบบปฏิบัติการที่แก้ตัวเองได้จากการพูดคุย

หน้านี้สรุป **transcript ช่วง 0:02–16:23 ที่ผู้ใช้ส่งมา** ไม่ใช่บทสรุปตอนเต็ม ตัวเลขทั้งหมดเป็นการเล่าจากความจำของผู้พูด ไม่ใช่ผล benchmark และวันที่ ingest ไม่ใช่วันเผยแพร่คลิป

## ให้ agent ใช้ช่วงที่รอคนตอบเป็นเวลาทำงาน (0:02–0:31)

เรื่องแรกคือ agent ไปหาวิธีเร่ง installer ของ Omarchy เจอเอง แล้ว DHH บอกว่าเป็นวิธีที่เขาเองยังไม่ได้คิดถึง

ตอนติดตั้ง ระบบต้องถามคนอยู่ราวห้าคำถาม เช่น username, password, time zone เดิมลำดับคือถามให้ครบก่อน แล้วค่อยลงมือทำงานหนัก agent เสนอให้มองช่วงที่รอคนพิมพ์เป็นโอกาส คือเริ่มโหลดของไว้เบื้องหลังระหว่างคนยังตอบคำถามอยู่

DHH ยอมรับว่านี่เป็นมุกเก่าที่สุดในวงการ เกมทำแบบนี้มานาน คือให้ผู้เล่นกดอะไรเล่นไปก่อนแล้ว preload ฉากถัดไปอยู่ข้างหลัง แต่เขาไม่เคยคิดจะเอามาใช้กับ installer

ผลคือ agent ช่วยได้แม้ในงาน optimization ที่ถือว่าต้องใช้ประสบการณ์ ประเด็นน่าสนใจไม่ใช่ว่ามันคิดวิธีใหม่ในโลก แต่มันหยิบ pattern มาตรฐานจากอีกวงการมาวางในที่ที่คนคุ้นเคยเกินจะเห็น

## รีดขนาด ISO แบบช่างรถ McLaren (0:31–3:59)

ส่วนที่เหลือของความเร็วมาจากขนาดไฟล์ เพราะเวลาส่วนใหญ่ของการติดตั้งหมดไปกับการคลาย package ที่บีบอัดไว้ ดังนั้นถ้า ISO เล็กลง เวลาติดตั้งก็ลดลงเกือบเป็นสัดส่วนเดียวกัน

- Omarchy รุ่นก่อนหน้ามี ISO ราว 7.5 GB ตอนคุยกันเหลือราว 5.85 GB
- font ของ JetBrains ที่ Omarchy ใช้ package บน Arch ใหญ่ราว 200 MB เพราะรวมทุก variant แต่ระบบใช้แค่ monospace รุ่น nerd font patched ซึ่งราว 16 MB เขาจึงทำ package รุ่น slim เอง ประหยัดไปราว 180 MB
- package ของ Nvidia driver ที่มาจาก repo ของ Arch ยังไม่ได้บีบอัดด้วย zstd ระดับแรงสุด การบีบอัดแบบนี้ใช้เวลาสร้างนาน แต่เขามองว่าตอน build package มีเวลาเหลือเฟือ ถ้าแลกมาด้วย ISO ที่เล็กลง แค่สอง package นี้ประหยัดไปราว 200 MB

เรื่อง font มีเกร็ดว่าตอนแรกเขาไม่ชอบ JetBrains font แต่ย้ายมาใช้เพราะเป็น font เดียวที่เรนเดอร์สวยใน Ghostty ซึ่งเป็น terminal ของ Mitchell Hashimoto ส่วน Bitstream Vera Sans ที่เขาใช้มานานกลับออกมาไม่เหมือนที่เคยเห็น

> "They are absolutely obsessed with shaving every damn last gram off their cars."
>
> เขาเทียบตัวเองกับวิศวกร McLaren ที่คลั่งการโกนน้ำหนักออกจากรถทีละกรัม (2:55–3:59)

เขาเล่าว่าเคยเห็นสัมภาษณ์ทีม McLaren คุยกันว่าลดน้ำหนักได้ 370 กรัมจากชิ้นหนึ่ง บนรถที่หนักเป็นพัน ๆ กิโล แล้วรู้สึกทั้งขำและชอบ พอมานั่งไล่โกน megabyte ออกจาก package เขาเลยรู้สึกว่ากำลังทำงานแบบเดียวกัน

ผลคือ เมื่อการลงมือแก้ถูกลงเพราะมี agent ช่วย งาน optimization จุกจิกที่เมื่อก่อนไม่คุ้มเวลาคนก็กลับมาคุ้มอีกครั้ง ข้อควรระวังคือคลิปไม่ได้บอกว่าเขาใช้เวลาไปเท่าไรกับการรีดขนาดครั้งนี้ จึงยังเทียบต้นทุนกับผลไม่ได้ตรง ๆ และการโกนของทิ้งทีละชิ้นก็มีความเสี่ยงแบบ [[local-optimization-trap|local optimization trap]] คือดีขึ้นเฉพาะจุดที่วัด แต่ไปพังเรื่องอื่นที่ไม่ได้วัด

## Omakase: ระบบที่เชฟเลือกของให้ (4:21–6:00)

พอพูดถึงขนาดไฟล์ก็เข้าเรื่องที่เขาเถียงกับสาย Linux ดั้งเดิมมานาน คือคำว่า bloat หรือของที่ใส่มาเกินจำเป็น

ในบางวงการถือว่าการแจก distribution ที่ลงโปรแกรมมาให้แล้วเป็นเรื่องไม่ควรทำ เพราะไม่ใช่หน้าที่ใครจะมาตัดสินว่าคนอื่นควรใช้โปรแกรมอะไร DHH สวนว่าชื่อระบบมันบอกอยู่แล้ว **Omarchy มาจากคำว่า omakase หรือให้เชฟเลือกให้** เขาเป็นเชฟ เขาเลยเลือก

> "I'm the chef. I'm making the choices. And this is the collection of applications I think is awesome." (4:35)

ของที่ลงมาให้ในเครื่องมีทั้ง OBS สำหรับอัดหน้าจอ, Kdenlive ซึ่งเป็น video editor แบบ timeline ที่เขาใช้ตัดวิดีโอทั้งหมดเอง, Neovim, [[herdr|Herdr]], tmux, terminal, ธีมและภาพพื้นหลังชุดที่เขาคัดแล้ว

เขายังเขียนเครื่องมือของตัวเองเพิ่มชื่อ Omacut สำหรับตัดคลิปสั้น เพราะการเปิด timeline editor ทั้งตัวเพื่อตัดคลิปหนึ่งอันมันน่ารำคาญ Omacut ขับด้วยคีย์บอร์ดทั้งหมด เลื่อนไปจุดเริ่มแล้วกด control+space เลื่อนไปจุดจบแล้วกด alt+space จากนั้น control+s เพื่อ save

> "This is supposed to be a productive system the minute you unpack it." (5:47)

ผลคือ เขายอมจ่ายพื้นที่บน ISO เพื่อให้เครื่องพร้อมทำงานตั้งแต่เปิดครั้งแรก ไม่ใช่ทะเลทรายที่ผู้ใช้ต้องประกอบเองใหม่ทั้งหมด ตรงนี้กลายเป็นแนวคิด [[omakase-software|Omakase Software]] ที่หน้านี้แยกออกไปเขียนต่อ

## Agent เขียน bash ได้แล้ว แต่ยังต้องดัดสไตล์ (6:01–7:15)

ส่วน configuration ของ Omarchy เขียนด้วย bash เป็นหลัก เพราะ bash ถูกออกแบบมาสำหรับงาน system administration พอ Lex ถามว่า agent เขียน bash ได้ดีแค่ไหน DHH ตอบว่าดี ยกเว้นเรื่องเดียว

> "I have to smack the agents over the back of the head every single time I catch it and remind it to look at the agents MD file because I will have an instruction in there not to make early exits. The agents love to have preconditions instead of fully expanded conditionals."
>
> เขาต้องคอยเตือน agent ให้กลับไปอ่าน `AGENTS.md` ทุกครั้งที่จับได้ เพราะในไฟล์มีข้อห้ามเรื่อง early exit อยู่ agent ชอบเขียนเป็น precondition แล้ว exit ทีละอัน ต่อกันไปเรื่อย ๆ จนตกมาถึงงานจริงที่มันจะทำ ส่วนเขาชอบแบบ `if this then do that` ที่กระจายเงื่อนไขให้ครบ (6:22–6:43)

เรื่องนี้มีสองชั้น ชั้นแรกคือความชอบด้าน style ของโปรแกรมเมอร์คนหนึ่ง ชั้นที่สองที่น่าสนใจกว่าคือ **เขาเขียนกฎไว้ในไฟล์แล้ว แต่ยังต้องเตือนซ้ำ** ตรงนี้เป็นข้อสังเกตเรื่องการทำตามคำสั่ง ไม่ใช่แค่เรื่องรสนิยม ดู [[claude-md|ไฟล์คำสั่งประจำ repo]] และ [[instruction-budget|Instruction Budget]]

ที่พลิกจากคลิปก่อนคือ ครั้งก่อนเขาเล่าว่าเคยขอ bash จาก agent แล้วพิมพ์เองใหม่ เพราะกลัวว่าความสามารถจะไหลออกจากนิ้วตัวเอง ถึงขั้นไปตั้งใจเรียน bash ให้เขียนได้จริง คลิปนี้เขาบอกว่า

> "I have not written any bash myself for probably a couple of months because the agents have just gotten so good." (6:43–7:15)

ผลคือ เจ้าตัวเปลี่ยนจุดยืนเองภายในไม่กี่เดือน หน้านี้ไม่ตัดสินว่าอันไหนถูก เก็บทั้งสองไว้เทียบใน [[skill-atrophy|Skill Atrophy]] เพราะเขาเรียน bash ไปแล้วก่อนจะเลิกเขียน ซึ่งไม่เหมือนคนที่ไม่เคยเขียนเองมาก่อนเลย

## คำสั่งที่ยังต้องพูดเองคือ "ทำให้ง่ายกว่านี้" (7:15–9:14)

นี่เป็นแก่นของคลิป DHH เล่าว่าสิ่งที่ agent ยังไม่ทำเองคือการลดความซับซ้อน และที่แปลกคือให้ agent อีกตัวมา review ก็ยังไม่จับ

> "It blows my mind how often an agent can do something, say it's done, have the work reviewed by another agent, they say it's done, and then I go like, 'Ah, looks a little too complicated for me.' And then it'll go like, 'Oh, yeah, you're right. I totally over complicated this.' And it'll cut it in half."
>
> agent ทำงานเสร็จบอกว่าเสร็จ agent อีกตัว review ก็บอกว่าผ่าน แต่พอเขาทักว่าดูซับซ้อนเกินไปหน่อย มันตอบว่าใช่ แล้วตัดเหลือครึ่งเดียว (7:15–7:45)

คำถามของเขาคือทำไมไม่ทำแบบนั้นตั้งแต่แรก แล้วมีคนเตือนเขาว่าคนก็เป็นแบบนี้ ทำงานเสร็จส่งให้เพื่อนดู เพื่อนบอกว่าดูซับซ้อนไปนะ เราก็มักเห็นด้วยและตัดออกได้

เขาสรุปว่ากลไกจับผิดยุคนี้เปลี่ยนที่ไป มุกเก่าคือบอก agent ว่า "อย่าทำผิด" ตอนนี้ไม่ต้องบอกแล้วเพราะ harness รัน test อัตโนมัติและป้อน feedback กลับให้เอง

> "But you actually do have to tell them, 'Make it simpler.'" (9:06–9:14)

และนี่คือเหตุผลที่เขาเชื่อว่าโปรแกรมเมอร์ยังจำเป็น ไม่ใช่เพราะต้องแกะสลักทุกบรรทัดเอง แต่เพราะต้องมีคนรู้สึกได้ว่าสัดส่วนของงานเพี้ยน เขาเปรียบตัวเองเป็น Da Vinci ที่มีลูกศิษย์ทั้งสตูดิโอช่วยสกัดหิน แล้วเขาเดินมาบอกว่าสัดส่วนยังไม่ได้

> "I can tell you when the argument doesn't land. I can tell you when the shape isn't proportional to the problem or when it just feels like it's too complicated." (8:46)

ผลคือ บทของคนขยับไปเป็น editor ที่ให้ feedback เรื่องรูปทรงและสัดส่วน แนวคิดนี้แยกไปเขียนต่อที่ [[make-it-simpler|Make It Simpler]] และเป็นหลักฐานที่ควรอ่านคู่กับ [[adversarial-review-loops|Adversarial Review Loops]] ว่า agent reviewer จับ bug ได้ไม่เท่ากับจับความซับซ้อนเกินจำเป็น

## เรื่องเสียง: DHH พิมพ์ Lex พูด (9:14–13:38)

หัวข้อถัดมาเป็นเรื่องรูปแบบการป้อนคำสั่ง แล้วสองคนใช้ต่างกันชัดเจน

DHH บอกว่า Omarchy มี [[voxtype|VoxType]] ซึ่งเป็นเครื่องมือถอดเสียงเป็นข้อความแบบ open source ให้ใช้ กดค้าง F9 แล้วพูดได้เลย ใช้กับคำสั่งสั้น ๆ ได้ดี แต่ package ไม่ได้ลงมาในเครื่องตั้งแต่แรกเพราะมี model ขนาดราว 150 MB เขาไม่อยากแบกน้ำหนักตรงนั้นบน ISO จึงทำเป็นตัวเลือกให้ติดตั้งตอนออนไลน์แทน ที่สำคัญกว่านั้นคือเขาบอกว่าตัวเองไม่ได้คิดด้วยการพูด ชอบพูดในรถ แต่พอมานั่งหน้าคีย์บอร์ดก็อยากพิมพ์

Lex ทำตรงข้าม เขาใช้ Plaud ซึ่งเป็นอุปกรณ์อัดเสียงติดเสื้อ กดปุ๊บอัดเลย แล้วเอาเสียงเข้า pipeline ต่อ ที่สำคัญคือ **เขาไม่ได้พูดสั้น ๆ เขาพูดยาว** บ่อยครั้ง 10–20 นาที บางครั้งเป็นชั่วโมง เป็นการคิดออกมาดัง ๆ รวมทั้งช่วงที่เปลี่ยนใจกลางทางเรื่อง design ก็ปล่อยให้อยู่ในเสียงนั้นด้วย

pipeline ของเขามีสองชั้น ชั้นแรกคือถอดเสียง เขาใช้ [[elevenlabs|ElevenLabs]] และบอกว่าเป็น speech-to-text ที่ดีที่สุดที่เขาลอง ชั้นที่สองคือ LLM ทำความสะอาด transcript โดยมี dictionary คำเฉพาะของเขา และมี agent ที่ไปกวาด code base เพื่อดึงชื่อไฟล์ ชื่อ function และคำที่เขาพูดถึงบ่อยมาช่วย เวลาคุยเรื่องข้อความก็ให้รู้จักชื่อคนใน Gmail กับ WhatsApp ด้วย

> "It doesn't have the problem of over specification. Because of how much stream of consciousness thinking the system has about what you're imagining." (10:58–11:22)

จุดที่ Lex ชอบคือ prompt แบบนี้ไม่แน่นเกินไป เพราะ agent ได้เห็นทางที่เขาคิดทั้งหมด ไม่ใช่แค่ข้อสรุปที่กลายเป็นข้อกำหนดตายตัว เขาบอกว่าเหมาะมากกับ design ช่วงต้น ถ้าจะสร้าง Omarchy ใหม่หมดเขาจะเริ่มด้วยการพูด

DHH ยอมรับว่ายังไม่เคยลองพูดยาวต่อเนื่อง 20 นาที เคยลองแค่สองสามประโยคแล้วรู้สึกว่าพิมพ์เองยังเร็วกว่า ส่วน Lex ชี้ว่าตอนใช้กับอีเมลจะเจอปัญหาอีกแบบ คือมันพลาดคำเล็ก ๆ แล้วต้องกลับไปแก้ แต่กับ agent เรื่องนั้นไม่สำคัญเท่า

ผลคือ ทั้งสองแบบใช้ได้ แต่ใช้ได้กับงานคนละชนิด สั่งสั้นเพื่อสั่งงาน กับพูดยาวเพื่อพา agent เข้าใจโจทย์ตอนต้น แยกไปเขียนต่อที่ [[voice-first-prompting|Voice-First Prompting]]

## ยอมให้ช้าได้ ถ้าเมื่อก่อนทำไม่ได้เลย (13:38–14:50)

ตรงนี้เป็นข้อคิดเรื่องการปล่อยของ Lex บอกว่าเขายอมรอ 5–10 วินาทีให้ pipeline ทำงานให้เสร็จได้ ไม่จำเป็นต้อง real time DHH เห็นด้วยและขยายเป็นหลักการ

> "Don't let the perfect be the enemy of good." (14:06)

เขายกตัวอย่าง iPhone รุ่นแรกที่แย่หลายอย่าง เน็ตช้ามาก เครื่องอ่อน แต่ตัวสินค้าน่าใช้พอที่คนไม่สนข้อเสียเหล่านั้น

> "If you're solving a problem that people currently don't have a solution for, they're willing to give it 5 seconds. If you're going to a competitive market, yeah, okay, it's different, but that means the problem's already solved and you don't need to solve it." (14:24–14:50)

ผลคือ เกณฑ์เรื่อง latency ขึ้นอยู่กับว่าตลาดนั้นมีของอยู่แล้วหรือยัง ถ้ายังไม่มีใครแก้ได้เลย ความช้าเป็นราคาที่คนยอมจ่าย ถ้ามีของเทียบอยู่แล้วก็ต้องคิดใหม่ นี่เป็นหลักตัดสินใจของผู้พูด ไม่ได้มีข้อมูลผู้ใช้ในคลิปมายืนยัน

## ระบบปฏิบัติการที่คุยแล้วเปลี่ยนรูปได้ (15:31–16:23)

ปิดท้ายด้วยภาพที่ DHH อยากเห็น เขาบอกว่า Omarchy รุ่นที่สี่ที่เรียกว่า Omarchy Quattro ในคลิป ดีมากในฐานะระบบที่ดัดแปลงได้ เพราะเพิ่มความสามารถได้ด้วยการคุยกับ agent ขั้นต่อไปคือรวมเรื่องเสียงเข้าไปด้วย

ตัวอย่างที่เขายกคือคนพูดกับเครื่องว่าอยากได้ panel ดูราคาหุ้น ขอ Apple กับ Dell แล้ว agent ก็ไปทำมาให้ ทั้ง input และ output เป็นเสียง ระบบปฏิบัติการเปลี่ยนรูปตามที่สั่ง เขาเทียบกับภาพ Jarvis ใน Iron Man และแอปที่เกิดขึ้นเฉพาะกิจ

> "Why can't we just talk to it and ask it to be a different way or change, and it'll all just change?" (16:23)

เขาโยงกับ AI สาย live gaming model ที่สร้างเฟรมถัดไปของเกมขึ้นมาสด ๆ แล้วคนเล่นได้จริง ถ้าทำกับเกมได้ ทำไมทำกับระบบปฏิบัติการไม่ได้ ตรงนี้เชื่อมกับ [[world-models|World Models]], [[malleable-tools|Malleable Tools]] และ [[just-in-time-software|Just-in-Time Software]]

ผลคือ เป็นภาพอนาคตที่ผู้พูดเสนอ ไม่ใช่ของที่มีอยู่ คลิปไม่ได้พูดถึงเรื่อง permission, ความปลอดภัย, การย้อนกลับเมื่อ agent แก้เครื่องพลาด หรือความคงเส้นคงวาของ UI ที่เปลี่ยนรูปได้ทุกวัน ซึ่งเป็นคำถามที่ต้องตอบก่อนใช้จริง

## เทียบกับ wiki เดิมและเรื่องที่ยังตอบไม่ได้

- **จุดยืนเรื่องเขียน bash เองสวนทางกับคลิปก่อน** ครั้งก่อน DHH ตั้งใจเรียน bash เพื่อไม่ให้ทักษะหาย ครั้งนี้เขาไม่ได้เขียนเองมาสองเดือนกว่า เก็บทั้งสองข้างไว้ใน [[skill-atrophy]] คำถามที่ยังไม่มีคำตอบคือทักษะที่เคยฝึกไว้แล้วอยู่ได้นานแค่ไหนเมื่อเลิกใช้ และคนที่ไม่เคยฝึกจะทักได้เท่าเขาไหม
- **agent review ไม่ได้แทน judgement ของคน** [[adversarial-review-loops]] เก็บเคสที่ agent reviewer จับ bug ยาก ๆ ได้ ส่วนคลิปนี้บอกว่า reviewer เดียวกันปล่อย code ที่ซับซ้อนเกินไปผ่านได้ สองอย่างไม่ขัดกัน แต่ต้องอ่านคู่กันว่า reviewer จับอะไรและไม่จับอะไร ยังไม่มีข้อมูลว่าถ้าตั้ง objective ของ reviewer ให้เน้นความเรียบง่ายโดยตรงแล้วผลจะเปลี่ยนไหม
- **"ไม่ต้องบอกว่าอย่าทำผิดแล้ว" ยังเป็นความเห็น** [[llm-coding-pitfalls]] กับหน้า [[model-honesty]] ยังเก็บหลักฐานว่า agent ประกาศว่าเสร็จโดยหลักฐานยังบางอยู่ต่อไป คลิปนี้เล่าประสบการณ์ว่า harness ที่รัน test เองช่วยเรื่องนี้ได้มาก เก็บทั้งสองไว้ ไม่ลบข้อใด
- **ตัวเลขทั้งหมดเป็นการเล่า** 7.5 GB, 5.85 GB, 180 MB, 200 MB, 150 MB, 370 กรัม เป็นตัวเลขที่ผู้พูดกะจากความจำ ไม่มีหน้า release note มาอ้างในคลิป
- **ยังไม่รู้ว่าการโกนขนาดกระทบอะไร** การตัด variant ของ font และบีบอัดแรงขึ้นมีข้อแลกเปลี่ยนอยู่ เช่น เวลา build ที่นานขึ้น หรือคนที่ต้องใช้ variant ที่ถูกตัดออก คลิปไม่ได้พูดถึง

## หมายเหตุเรื่องชื่อใน transcript

transcript ที่ส่งมาเป็นการถอดเสียงอัตโนมัติ ชื่อเฉพาะหลายคำเพี้ยน หน้านี้แก้จากบริบทดังนี้ `Hamachi` / `Umachi` / `Amachi` / `Omachi` → **Omarchy**, `Umacut` → **Omacut**, `Ghosty` → **Ghostty**, `Herder` → **Herdr**, `box type` / `Vox Type` → **VoxType**, `11 Labs` → **ElevenLabs**, `WhisperFlow` → **Wispr Flow** ซึ่งเป็นสปอนเซอร์ของรายการด้วย

ที่ยังไม่ยืนยัน: `Parrot model` ที่ VoxType ใช้ ผู้พูดเองก็บอกว่าจำไม่แน่ (เดาได้ว่าอาจเป็นตระกูล Parakeet ของ Nvidia แต่หน้านี้ไม่บันทึกเป็นข้อเท็จจริง) และ `Omachi Quattro` บันทึกเป็น **Omarchy Quattro** ตามที่ผู้พูดออกเสียง โดยยังไม่ได้ตรวจกับ release ของโครงการว่าเป็นชื่อรุ่นทางการหรือไม่ ลองดึง transcript ตอนเต็มจาก lexfridman.com เมื่อ 2026-09-07 แล้วหน้าที่ได้กลับมาไม่มีช่วงนี้ จึงยังตรวจไม่ได้
