# The Components of Agent Memory / agent ควรจำอะไร และกลับมาตรวจความจำอย่างไร

Lance Martin ผู้เขียนบทความฝั่ง Engineering ของ [[anthropic|Anthropic]] บริษัทผู้สร้าง Claude อธิบายว่า memory ที่ใช้ข้าม session ต้องมีทั้งจังหวะจดตอนทำงาน และจังหวะกลับมาทบทวนทีหลัง การจดช่วยเก็บสิ่งสำคัญทันที ส่วน [[dreaming|dreaming]] คือการใช้เวลานอกงานหลักอ่านหลักฐานย้อนหลัง แก้บันทึก และจัดความรู้ให้นำกลับมาใช้ได้ง่าย

บทความนี้นับเฉพาะความรู้จากประสบการณ์ที่เก็บไว้ให้ session ถัดไปอ่าน ไม่รวมการฝึกน้ำหนัก model การเรียนรู้ภายในบทสนทนาเดียว หรือ [[compaction|การย่อประวัติเพื่อทำงานเดิมต่อ]]

## จากประวัติดิบไปถึงสิ่งที่โหลดไว้ให้ทุกครั้ง

[[agent-memory-hierarchy|ลำดับชั้นของ memory]] ในบทความมีสี่ชั้น แต่ละชั้นช่วยลดงานคนละแบบ

1. **Transcripts:** ประวัติการทำงานที่ค้นย้อนหลังได้ ใช้ตรวจว่าบันทึกสรุปมาจากอะไร
2. **Memory notes:** สิ่งที่ agent เลือกจด เช่น บทเรียน แผน และกฎที่ลองแล้ว
3. **Memory representations:** แผนที่ความรู้ เช่น [[llm-knowledge-bases|wiki ที่ LLM เขียนและเชื่อมหน้าไว้ให้]]
4. **Injected context:** ข้อมูลชุดเล็กที่ harness ซึ่งเป็นระบบรอบ model โหลดให้ตอนเริ่ม session

Dreaming แก้ข้อมูลได้หลายชั้น รวมถึงย้ายรายละเอียดลงจากชั้นบนแล้วเหลือลิงก์ไว้ **ผลคือ:** agent ไม่ต้องอ่านทุกอย่างก่อนเริ่มงาน แต่ยังย้อนหาหลักฐานได้

## จดแล้วต้องตรวจสมมติฐานด้วย

Continual Learning Bench หรือ CL-Bench 1.0 เป็นชุดทดสอบการเรียนรู้จากงานต่อเนื่อง ในงานฐานข้อมูลที่บทความใช้ แต่ละคำถามเริ่ม session ใหม่ผ่าน [[claude-managed-agents|Claude Managed Agents]] แพลตฟอร์มรัน agent ของ Anthropic มีเพียงโฟลเดอร์ memory ที่ส่งต่อกัน และ agent ได้เฉลยหลังตอบ

ผลที่รายงานแสดงว่า model ใช้โฟลเดอร์เดียวกันได้ต่างกันมาก Sonnet 4.6 มักเก็บข้อสันนิษฐานที่ยังไม่ตรวจ ส่วน Opus 5 ทดสอบสมมติฐานแล้วเก็บทั้งกฎ หลักฐาน และจุดที่เคยพลาด คะแนนเฉลี่ยของ Opus 5 ขยับจาก 0.564 เมื่อไม่มี memory เป็น 0.828 เมื่อมี ขณะที่ Sonnet 4.6 ขยับจาก 0.330 เป็น 0.364

เมื่อสั่ง Sonnet 4.6 ให้กลับมาอ่าน memory และทดสอบข้อสันนิษฐาน คะแนนขึ้นเป็น 0.641 แต่กฎให้จดเฉพาะความล้มเหลวกลับลดประโยชน์ของ memory ใน Opus 4.7 และ Opus 5 **ได้อะไร:** ต้องวัดทั้งคุณภาพบันทึกและการนำไปใช้ คำสั่งที่ช่วย model รุ่นหนึ่งอาจรบกวนอีกรุ่น

## เลือกสิ่งที่ควรจำ แทนการจดทุกเหตุการณ์

ในการเล่น Pokémon Red ที่นำมาเปรียบเทียบอย่างละหนึ่งรอบ ช่วงประมาณ 10,000 ขั้น Sonnet 3.7 มี memory 413 ไฟล์และได้หนึ่งเข็มกลัด ส่วน Fable 5 มีสิบไฟล์รวมไฟล์หลัก และได้สี่เข็มกลัด

Sonnet 3.7 เก็บสถานะที่อ่านจากหน้าจอใหม่ได้อยู่แล้ว จนเสียเวลาจัดบันทึกที่ล้าสมัย Fable 5 เน้นเป้าหมาย แผน และวิธีเล่นที่ค้นพบเอง **ผลคือ:** ควรเก็บสิ่งที่ช่วยตัดสินใจรอบหน้า โดยเฉพาะสิ่งที่กู้จากสภาพปัจจุบันไม่ได้ ตัวอย่างนี้ยังแยกผลของความเก่ง model ออกจากรูปแบบ memory ไม่ได้

## Dreaming กลับไปแก้ความจำผิด

ในอีกตัวอย่างหนึ่ง Claude จำด้านของภูเขา Mt. Moon ผิด พอออกจากอาคารก็คิดว่าผ่านถ้ำแล้ว จึงเดินตกขอบทางและวนกลับ การทบทวน transcript ทำให้มันแก้บันทึกตำแหน่ง แล้วกลับเข้าถ้ำจนไปถึงเมืองถัดไป

นี่เป็นตัวอย่างของ [[memory-drift|ความจำที่พา agent ตัดสินใจผิด]] ซึ่งอาจผิดตั้งแต่จด ไม่จำเป็นต้องเก่าเสียก่อน **ได้อะไร:** เวลาบันทึกขัดกัน ต้องย้อนดูหลักฐาน ไม่ใช่เชื่อข้อความล่าสุดเพียงเพราะใหม่กว่า

## Wiki ช่วยเมื่อใด และเมื่อใดไม่คุ้ม

Anthropic ทดลองสร้าง wiki จากเอกสารภายใน Stainless ราว 350,000 ไฟล์หรือ 420 ล้าน tokens แล้ววัดด้วยคำถาม 25 ข้อ เมื่อเพิ่มรอบสร้าง wiki จากสองเป็น 128 session ผลที่รายงานเป็นสัดส่วนเกณฑ์ที่ตอบได้ ไม่ใช่จำนวนคำถามที่ถูกทั้งข้อ

| วิธีตอบ | คะแนนที่รายงาน |
|---|---|
| ค้นเอกสารอย่างเดียว | 53% |
| ใช้ wiki อย่างเดียว เมื่อ wiki โตขึ้น | 13% → 48% |
| ใช้ wiki ร่วมกับการค้นเอกสาร เมื่อ wiki โตขึ้น | 54% → 61% |

แบบ wiki ร่วมกับการค้นยังใช้ tokens ตอนตอบน้อยลงราว 20,000 ต่อคำถาม แต่ต้องนับต้นทุนสร้างและดูแล wiki เพิ่มด้วย

การทดลองเรื่องควบรวมกิจการอีกชุดมี 24 คำถาม สำหรับกลุ่มที่ต้องเชื่อมหลายเอกสารหรือใช้วิจารณญาณ/คำนวณ คะแนนจาก wiki อยู่ที่ 87% เทียบกับการค้นอย่างเดียว 73% ขณะที่งานหนึ่งใน Harvey LAB ซึ่งเป็นชุดทดสอบงานกฎหมาย ค้นคำตอบจากเอกสารเดียวได้เกือบหมด จึงไม่เห็นประโยชน์ชัด อีกงานสร้าง wiki 203 KB จากต้นฉบับ 115 KB จนแทบไม่ได้ช่วยย่อความรู้

**ผลคือ:** wiki มีประโยชน์เมื่อช่วยเชื่อมเรื่องที่ต้องใช้ซ้ำ ไม่ควรถือว่าแทนการค้นต้นฉบับได้เสมอ

## ชั้นที่โหลดทุก session ต้องเล็กและตรงงาน

Injected context ช่วยให้ agent เห็นเรื่องสำคัญโดยไม่ต้องรู้ก่อนว่าควรค้นหาอะไร แต่ข้อความผิดก็อาจติดไปทุก session และการใส่ข้อความไว้ไม่ได้รับประกันว่า model จะทำตามทั้งหมด จึงต้องคุม [[instruction-budget|ปริมาณคำสั่งที่ model ต้องรับพร้อมกัน]] และย้ายรายละเอียดไปอ่านเมื่อต้องใช้

การจัด wiki ต้องรู้ด้วยว่างานปลายทางต้องรักษาอะไร ในงานสัญญาหนึ่งของ LAB หลาย agent เขียนตารางเดียวกันจนทับข้อมูลกัน บวกกับสรุปเงื่อนไขไม่ครบ จึงเก็บได้ 41 จาก 57 ข้อ พอเปลี่ยนเป็นหนึ่ง agent ต่อหนึ่งหน้าสัญญาและรักษาถ้อยคำเงื่อนไขให้ตรงต้นฉบับ ก็เก็บได้ครบ 57 ข้อ

Dreaming รอบถัดไปยังช่วยแก้ลิงก์ไปหน้าที่ไม่มีอยู่และเติมหน้าที่ขาด **ได้อะไร:** ต้องตรวจทั้งความถูกต้องของเนื้อหา การเขียนพร้อมกัน และทางเดินระหว่างหน้า

## เรื่องที่ยังต้องตัดสินใจ

จดระหว่างทำงานแล้วใช้ต่อได้เร็ว แต่แย่งความสนใจจากงานหลัก ส่วนการทบทวนเบื้องหลังไม่ขวางงานตรงหน้า แต่ผลอาจมาช้า การตรวจทุกบันทึกตลอดเวลาก็ใช้ compute มาก บทความจึงยังเปิดคำถามเรื่องรอบทบทวน ความสดของข้อมูล และความคุ้มค่าของแต่ละชั้น
