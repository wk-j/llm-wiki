# State of Technology and the Joy of Making / เทคโนโลยีกับความสุขจากการลงมือสร้าง

โพสต์นี้คือบันทึกความรู้สึกของ [[phoomparin-mano|Phoomparin Mano]] (นักสร้าง software และผู้ใช้ agent workflow) ต่อวงการเทคโนโลยีในยุค coding agent. เขาดีใจที่ [[claude|Claude]] ช่วยให้คนแก้ปัญหาของตัวเองและแบ่งเครื่องมือให้คนอื่นใช้ได้ โดยไม่ต้องรอ technologist ทุกเรื่อง. แต่เขากังวลว่า software กำลังกลายเป็นงานผลิตแบบเน้นผลลัพธ์ล้วน ๆ จนความสนุกจากการเรียนรู้ ค่อย ๆ เก่งขึ้น และตัดสินใจรายละเอียดด้วยตัวเองหายไป.

แก่นของโพสต์จึงไม่ใช่ “ใช้ AI หรือไม่ใช้ AI”. ผู้เขียนบอกว่าตัวเองทำ agent workflow ได้คล่องและมีประสิทธิภาพมากแล้ว. ความขัดแย้งอยู่ตรงที่ยิ่ง workflow ดี เขายิ่งรู้สึกห่างจากสิ่งที่สร้าง และตอบยากขึ้นว่ายังพูดได้เต็มปากไหมว่า “yeah I built this!”.

โพสต์ปิดท้ายว่าเป็น `Friends only`. หน้านี้จึงเก็บเฉพาะสาระสรุปกับวลีสั้นที่จำเป็น ไม่คัดลอกต้นฉบับเต็ม. Browser ที่ผู้ใช้อนุญาตให้เข้าถึงแสดงชื่อผู้เขียน, permalink และเวลาแบบ relative `15h` ในวันที่ ingest; วันที่เผยแพร่จึงบันทึกเป็น 2026-08-25.

## สองด้านที่ผู้เขียนพยายามถือไว้พร้อมกัน

ด้านแรกคือ AI ลดกำแพงการสร้าง. คนที่ไม่ได้เป็น developer เต็มตัวเริ่มทำเครื่องมือแก้ปัญหาของตัวเองได้ และ community ไทยเริ่มนำ Claude ไปทำสิ่งที่มีประโยชน์ให้คนอื่น. นี่คือ democratization ที่ผู้เขียนมองว่าเป็นจุดเริ่มต้นที่ดี.

อีกด้านคือข่าวนอก bubble ไทย จีน และเอเชียตะวันออกเฉียงใต้ทำให้เขาเห็นภาพที่มืดกว่า. เขายก Big Tech, surveillance capitalism, ผลกระทบต่อชุมชน และผลิตภัณฑ์ที่บั่นทอนความสุขของมนุษย์. ประเด็นเหล่านี้เป็นข้อกังวลในโพสต์ ไม่ใช่ claim ที่หน้านี้ตรวจสอบแยกแล้ว.

ผู้เขียนเรียกกรอบนี้ว่า polarity management คือไม่เลือกขั้วว่าเทคโนโลยีดีทั้งหมดหรือเลวทั้งหมด. ไม่กลัวเทคโนโลยีเป็นเรื่องดี แต่ถ้าปล่อยให้ด้านเดียวกินพื้นที่ทั้งหมด ผลเสียจะย้อนกลับมา.

**ได้อะไร:** ต้องประเมินเทคโนโลยีทั้งจากสิ่งที่มันเปิดให้คนทำได้ และจากนิสัย คุณค่า กับโครงสร้างอำนาจที่มันทำให้เติบโต.

## เมื่อ software เหลือแค่ของที่ต้องผลิต

ผู้เขียนคิดถึงยุคที่คนค่อย ๆ เรียน code, math หรือ Linux kernel แล้วได้ความภูมิใจจาก mastery ที่สะสมทีละนิด. ในสายตาเขา วงการตอนนี้กลับถามว่าเมื่อโยน [[fable|Fable]] เข้า agent loop แล้วได้ software ใช้งาน ทำไมต้องเรียนหรือสนุกกับวิธีทำอีก.

เขาเชื่อมความรู้สึกนี้กับประโยค “coding is solved” ที่อ้างถึง [[boris-cherny|Boris Cherny]]. หน้านี้ยังไม่ได้ตรวจบริบทต้นทางของประโยค จึงเก็บไว้ในฐานะสิ่งที่ผู้เขียนตอบสนอง ไม่ใช้เป็นจุดยืนสมบูรณ์ของ Boris.

ความกลัวจริงคือ เมื่อ generation ถูกพอและเร็วพอ สังคมอาจตีความ programming เป็นกิจกรรมที่มีไว้หาเลี้ยงชีพอย่างเดียว. ความสุขจากการลองผิดลองถูก หรือจากการตัดสินใจเล็ก ๆ ระหว่างทางถูกมองว่าไม่มีประโยชน์.

**ผลคือ:** [[programming-process-matters|process ของ programming]] มีคุณค่าอย่างน้อยสองแบบ. มันช่วยสร้างความเข้าใจเพื่อให้ระบบถูก และสร้างความหมายให้คนที่ลงมือทำ. Output ที่ทำงานได้พิสูจน์ได้เพียงแบบแรกบางส่วน.

## Agent workflow ที่ดีอาจยังทำให้คนห่างจากงาน

จุดที่ทำให้โพสต์มีน้ำหนักคือผู้เขียนไม่ได้พูดจากฝั่งที่ใช้ agent ไม่เป็น. เขาบอกว่า workflow ของตัวเอง optimal มากและไม่ได้ทำยาก. แต่ยิ่งใช้ เขายิ่งขาดความรู้สึกว่าเป็นคนสร้างงานนั้น เพราะการคิดและลงมือส่วนใหญ่มีตัวช่วย.

นี่คือ [[creative-ownership|Creative Ownership]] หรือความรู้สึกว่าเราได้สร้าง judgement และลายมือของตัวเองลงในงาน. มันใกล้กับเรื่องของ [[typecraft|Typecraft]] แต่ไม่เหมือน [[cognitive-surrender|Cognitive Surrender]] ทุกกรณี. คนอาจมี attention พอ ตรวจงานครบ และได้ output ดี แต่ยังรู้สึกห่างจากกระบวนการสร้างได้.

โพสต์ยังทำให้ [[code-is-free|Code is Free]] ต้องนับต้นทุนอีกชนิด. Implementation อาจถูกลง แต่ความภูมิใจ ความผูกพัน และแรงอยากเรียนรู้อาจไม่ได้ถูกลงตาม. ถ้า workflow เน้น throughput อย่างเดียว ต้นทุนนี้จะไม่โผล่ใน test หรือ dashboard.

**ได้อะไร:** workflow ที่ดีต้องถามทั้ง “งานผ่านไหม” และ “คนยังได้คิด ตัดสินใจ และรู้สึกเป็นเจ้าของส่วนที่สำคัญไหม”.

## Creative coding เป็นวิธีคืนคุณค่าให้ process

ข้อเสนอของผู้เขียนคือทำให้คนเห็นด้าน `creative coding` มากขึ้น. บางครั้งความสนุกไม่ได้อยู่ที่ของเสร็จ แต่อยู่ที่การแก้ปัญหาด้วยตัวเอง การปั้นงาน และการเลือก micro-decision จำนวนมาก.

เขาเล่าว่าคนสาย tech หลายคนหันไปหากิจกรรม offline เช่น ถักไหม เดินเขา ปีนผา วาดรูป หรือ sketch. สิ่งเหล่านี้ไม่ได้มีคุณค่าเพราะมีประสิทธิภาพที่สุด แต่เพราะ process ยังสัมผัสได้และคนเห็นความสัมพันธ์ระหว่างมือ การตัดสินใจ และผลงาน.

นี่ไม่ได้แปลว่าต้องทำทุกอย่างเอง. หลักที่ใช้ต่อได้คือเลือกเก็บ friction ที่เป็นส่วนของการเรียนรู้หรือความหมาย และให้ agent รับ friction ที่ไม่ใช่แก่น. ตรงกับคำถามใน [[skill-atrophy|Skill Atrophy]] ว่า “ทักษะนี้คือสิ่งที่กำลังอยากเรียนจริงไหม”.

**ผลคือ:** อย่าวัด creative coding ด้วยเวลาส่งมอบ. จุดหมายคือรักษาพื้นที่ที่คนได้ฝึก taste, curiosity และความสัมพันธ์กับงาน.

## เรื่องที่ยังตอบไม่ได้

- คนใหม่ที่สร้างของผ่าน prompt อาจรู้สึกมี agency มากขึ้น ขณะที่คนที่เคยลงมือทุกขั้นรู้สึกเสีย ownership. เทคโนโลยีเดียวกันจึงปลดล็อกคนหนึ่งและทำให้อีกคนห่างจากงานได้.
- การขยับขึ้น abstraction layer ใหม่เกิดซ้ำมาตั้งแต่ binary, assembly และภาษา high-level. ยังต้องแยกว่า friction ใดคือรายละเอียดที่ยินดีปล่อย กับ friction ใดเป็นแหล่งเรียนรู้และความหมาย.
- ผู้เขียนรู้สึกติดอยู่ระหว่างสองขั้ว: ฝั่งหนึ่งบอกว่า AI จะเอางานทั้งหมด อีกฝั่งโจมตีคนที่ใช้ AI. โพสต์ไม่ได้แก้ความขัดแย้งนี้ แต่ปฏิเสธการลดเรื่องให้เหลือเพียงเลือกข้าง.
- Big Tech, surveillance capitalism และผลกระทบต่อชุมชนเป็นคำเตือนระดับสังคมที่โพสต์กล่าวกว้าง ๆ. ต้องมี source เพิ่มหากจะใช้ยืนยันเหตุการณ์หรือ causality เฉพาะกรณี.
- ประโยค “coding is solved” ถูกเล่าผ่านโพสต์นี้โดยไม่มีลิงก์ต้นทาง. ความหมายที่ Boris ตั้งใจอาจต่างจากความหมายเชิงวัฒนธรรมที่ผู้เขียนกังวล.
