# Companies Use AI Productively but People Can't Keep Up / บริษัทใช้ AI ได้ผลจริง แต่คนตามไม่ทัน

โพสต์ Facebook จาก handle `@teepagorn` ขึ้นต้นว่า "ชีวิตติดเอไอ เสนอต๊อน" และเป็น shared post ผู้เขียนเล่าต่อจากที่ [[simon-willison|Simon Willison]] (developer รุ่นใหญ่ ผู้สร้าง Datasette ที่เขียนเรื่อง AI coding บ่อย) หยิบโพสต์ของ developer ชื่อ voxium มาแปะ แล้วตั้งคำถามว่า **พอ tool ทำงานได้ตามสัญญา ทำไมคนกลับเหนื่อยขึ้น และความเข้าใจของทีมหายไปไหน**

ข้อมูลที่ผู้ใช้ส่งมาไม่มีชื่อผู้เขียน วันที่โพสต์ permalink ของโพสต์ หรือลิงก์ไปโพสต์ของ Simon กับ voxium ส่วน title "Facebook" เป็นชื่อหน้า ไม่ใช่ชื่อบทความ wiki จึงตั้งชื่อตามเนื้อหา อ้างผู้เขียนด้วย handle เท่านั้น เหมือนหน้า [[teepagorn-ten-lessons-building-with-ai]] ที่มาจาก handle เดียวกัน

## 1. เรื่องของ voxium: ทุกอย่าง "Talk to Claude"

voxium เพิ่งเข้าบริษัทใหญ่แห่งหนึ่งได้ครึ่งเดือน แล้วพบว่าแทบทุกอย่างในทีมทำผ่าน [[claude-code|Claude Code]] ทั้ง spec, code, test, PRD, ticket, การแก้ ticket และ report ทุกระดับตั้งแต่ engineer L1 ถึง L7 ทำงานแบบเดียวกัน คือ "Talk to Claude."

ถ้าทำเป็นสไลด์ บริษัทนี้ดูเหมือน adopt AI สำเร็จเต็มร้อย ทุก level ใช้จริง output เพิ่มมาก ผู้เขียนยอมรับว่าส่วนนั้นจริง แต่คนในทีมไม่มีใครชอบ:

- ทุกคนถูกกดให้ ship ให้มากที่สุด ทำงานวันละ 12-13 ชั่วโมง "just to press enter"
- ผู้บริหารถามซ้ำว่า ไหนบอกว่า push code ไม่ใช่ bottleneck แล้วทำไมยังช้า
- ประโยคที่ผู้เขียนยกมาเป็นแก่น: **"Nobody is reading anything."**

**ผลคือ:** tool ไม่ได้ล้มเหลว มันทำได้ตามที่ promise เป๊ะ ปัญหาอยู่ที่องค์กรทำอะไรกับความเร็วที่ได้มา

## 2. เร็วขึ้นก็รับเพิ่ม: เวลาที่ได้คืนไม่ได้กลับไปที่การคิด

ผู้เขียนชี้ว่าพอผลิตได้เร็ว องค์กรไม่ได้เอาเวลาที่เหลือไปคิด คุย อ่าน หรือทำความเข้าใจงาน กลับเพิ่มของที่ต้องผลิตแทน เร็วขึ้นก็รับเพิ่ม เร็วขึ้นอีกก็ยกเป้าอีก สุดท้ายคนทำงาน 12-13 ชั่วโมงเพื่อไล่กด Enter ตาม output ของเครื่อง "ล้ำมากครับ เหนื่อยกว่าเดิม"

ผู้เขียนเดาเพิ่ม (บอกเองว่าเดา) ว่า management อาจตัดสินใจไม่ทันปริมาณงานที่ไหลขึ้นมาด้วย

กลไกนี้ตรงกับ [[ai-work-intensification|AI Work Intensification]] (ภาวะที่ AI ลด effort ต่อชิ้น แต่องค์กรเอาความเร็วไปยกเป้าจนงานรวมหนักขึ้น) และเป็น field report ชิ้นที่สามต่อจาก [[typecraft|Typecraft]] กับ [[dillon-mulroy|Dillon Mulroy]]

**ได้อะไร:** productivity gain ไม่ได้กลายเป็นเวลาคิดเอง ต้องมีคนตั้งใจจัดสรรมัน

## 3. อีกด้าน: ผู้เขียนเองก็ชอบ Claude Code มาก

ผู้เขียนไม่ได้ต่อต้าน tool เขาใช้ Claude Code เยอะและชอบจริง งานที่เคยใช้หลายวันเหลือไม่กี่ชั่วโมง ของที่เคยขี้เกียจ setup ก็ลองสร้างได้เลย experiment cost แทบเป็นศูนย์ เช่นอยากลองสร้าง CRM ก็ทำได้ทันที

แต่เขาใส่วงเล็บไว้ว่า deploy เป็นอีกเรื่อง test เป็นอีกเรื่อง เอาไปเจอปัญหาจริงก็อีกเรื่อง ที่เร็วมากคือ prototype ดู [[throwaway-prototyping]]

**ผลคือ:** ความเร็วช่วงสร้างของต้นแบบเป็นของจริง แต่ไม่ได้แปลว่าช่วงทำให้ใช้งานจริงเร็วตามไปด้วย

## 4. ยิ่งดูเรียบร้อย ยิ่งกด approve ง่าย

ผู้เขียนเล่าจากตัวเอง พอ AI ทำงานเก่ง หน้าตางานก็ดูครบ มีเหตุผล มี test มี documentation มีสรุปให้เสร็จ เขาอ่านแล้วเห็นว่าครบถ้วนเลยกด approve อย่างมั่นใจ "สามวันต่อมา สวัสดีครับ incident"

ตรงนี้คือ [[quality-proxy-collapse|Quality Proxy Collapse]] (สัญญาณคุณภาพผิว ๆ อย่างความเรียบร้อยหรือ test ที่มีครบ ใช้เดาคุณภาพจริงไม่ได้แล้ว) ผสมกับ [[cognitive-surrender|Cognitive Surrender]] (ยอมรับงาน AI ทั้งที่ยังไม่ได้ตั้งความเห็นเอง)

**ได้อะไร:** ความเรียบร้อยของ artifact ไม่ใช่หลักฐานว่าระบบถูก

## 5. อยู่ในทุกขั้นตอน โดยไม่เข้าใจสักขั้น

ส่วนนี้เป็นข้อสังเกตที่คมที่สุดของโพสต์ ถ้า AI เขียน spec แล้วเอา spec ไปเขียน code เขียน test ตรวจ code แล้วเขียน report สรุปให้อีกที คนจะอยู่ในทุกขั้นตอนได้โดยไม่เข้าใจขั้นไหนเลย

พอระบบพัง ผู้เขียนถามสามข้อ:

1. ใครรู้ว่า logic นี้มาจากไหน
2. test ผ่านเพราะระบบถูก หรือเพราะ test กับ code เชื่อ assumption ผิดอันเดียวกัน
3. ของที่ deploy ไปตรงกับที่ผู้ใช้ต้องการไหม

ข้อสองคือปัญหา error ที่ไปด้วยกัน พอ spec, code และ test มาจากแหล่งเดียว ความผิดตั้งต้นจะไหลผ่านทุกชั้นโดยไม่มีชั้นไหนจับได้

ถ้าคำตอบทุกครั้งคือ "เดี๋ยวถาม Claude" ความรู้ของทีมก็ไม่ได้อยู่ในทีมแล้ว มันกระจายอยู่ใน session เป็นร้อย ๆ อัน คนในทีมเลยไม่มี mental model ร่วมกันพอจะ challenge คำตอบของ AI ได้ ดู [[comprehension-debt|Comprehension Debt]] และ [[cognitive-debt|Cognitive Debt]]

**ผลคือ:** human-in-the-loop ที่แค่กด approve ไม่ใช่การตรวจ ถ้าทุกชั้นมาจาก AI ตัวเดียวกัน

## 6. วัด AI adoption ผิดจุด

ผู้เขียนบอกว่าองค์กรชอบวัดสิ่งที่นับง่าย เช่น พนักงานใช้กี่เปอร์เซ็นต์ ทำงานเร็วขึ้นเท่าไร ship มากขึ้นแค่ไหน เพราะทำ dashboard สวย ผู้บริหารดูแล้วชื่นใจ

เขาแซวเพิ่มว่าเคยมียุค [[tokenmaxxing|tokenmaxxing]] (ใช้ token เยอะเพื่อให้ดู productive) แต่ "ยุคนั้นได้ผ่านพ้นมาแล้ว ยุคนั้นสั้นเหลือเกินประมาณ 3 เดือนปะ" ข้อนี้เป็นความเห็นติดตลกของผู้เขียน ไม่มีข้อมูลรองรับ

คำถามที่ผู้เขียนอยากให้ถามแทน:

- คนในทีมยังอธิบายสิ่งที่ตัวเองส่งขึ้น production ได้ไหม
- ยังรู้ไหมว่าทำไมระบบเป็นแบบนี้
- ยังเถียงกับ AI ได้หรือเปล่า
- หรือเหลือแค่ AI ตัวหนึ่งสรุปงานของ AI อีกตัว ให้มนุษย์กด approve

ผู้เขียนคิดว่าเรื่องนี้ไม่ได้เกิดแค่บริษัทเทค องค์กรหลาย industry ก็น่าจะเป็นแนวนี้

**ได้อะไร:** metric ที่ควรมีคือคนยังอธิบายและโต้แย้งงานของตัวเองได้ ไม่ใช่แค่อัตราการใช้งาน

## 7. L1 ถึง L7 ทำงานเหมือนกัน แล้ว junior จะเรียนจากใคร

ผู้เขียนมองว่าจุดน่ากลัวอีกข้อคือทุก level ทำงานแบบเดียวกัน ทั้งที่คุณค่าของ senior ไม่ได้อยู่ที่เขียน code ได้มากกว่า junior อย่างเดียว แต่อยู่ที่การถือบริบท เห็น trade-off ทัก assumption รู้ว่าเรื่องไหนควรทำ และเรื่องไหนยังไม่ควรรีบ

ถ้าทุกระดับเหลือ workflow เดียวคือ prompt แล้ว ship ความ senior อาจเหลือแค่ใครเปิด agent พร้อมกันได้เยอะกว่า ใครกด Enter ได้ดึกกว่า หรือใครประชุมได้เยอะกว่า

ผู้เขียนถอยกลับมาครึ่งก้าวว่า judgement และความ "ดมกลิ่นได้" ว่าอะไรผิด น่าจะยังอยู่ แต่มันจะเริ่มไม่ถูกถ่ายทอด junior ไม่เห็นวิธีคิดของ senior แล้ว ส่วน senior ก็ไม่มีเวลาสอน เพราะตัวเองยังวิ่งตาม output ไม่ทัน ดู [[skill-atrophy]] และ [[engineering-role-shift]]

**ผลคือ:** ปัญหาไม่ใช่แค่ senior ใช้ judgement น้อยลง แต่เป็นทางส่งต่อ judgement ไปยังรุ่นถัดไปที่ขาด
