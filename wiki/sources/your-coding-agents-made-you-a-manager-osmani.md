# Your Coding Agents Made You a Manager / ใช้ agent เขียนโค้ด ก็ต้องสั่งงานและตรวจงานให้เป็น

[[addy-osmani|Addy Osmani]] ผู้เขียนเรื่องการพัฒนาซอฟต์แวร์และสมาชิกทีม Claude Code ที่ Anthropic ชวนสังเกตว่า ถึงเราจะยังมีตำแหน่ง developer แต่ถ้าใช้ coding agent ทั้งวัน เราก็กำลังเลือกงาน อธิบายเป้าหมาย มอบหมาย ติดตาม ตรวจผล และตัดสินใจว่าจะนำงานไหนไปใช้ ทั้งหมดนี้เป็นทักษะที่ผู้จัดการทีมต้องใช้เช่นกัน

เขาไม่ได้ชวนให้ทุกคนย้ายไปเป็นผู้จัดการ หรือบอกว่า agent แทนเพื่อนร่วมงานได้ ประเด็นคือ คนที่สั่งงานและตรวจงานเป็นมักใช้ agent ได้ผลดี และคนที่เคยรับงานคลุมเครือจากหัวหน้าก็น่าจะรู้ว่าต้องบอกอะไรเพิ่ม เพื่อไม่ให้คนรับงานต้องเดา

บทความเรียงคำแนะนำตามความสำคัญโดยคร่าว ๆ เริ่มจากการให้ agent ตรวจงานตัวเองได้ และจบที่การตัดสินใจของคนว่างานไหนควรทำ งานไหนควรหยุด

## บอก agent ว่าต้องตรวจอะไร แล้วขอผลตรวจทุกครั้ง

ถ้าบอกเพียงว่าให้แก้งานจนเสร็จ agent อาจหยุดเมื่อโค้ดดูเหมือนใช้ได้ Addy แนะนำให้เตรียมวิธีตรวจที่มันรันเองได้ เช่น test, build, linter หรือสคริปต์ตรวจผล และให้รายงานว่าใช้คำสั่งอะไร ได้ผลอย่างไร ถ้าแก้ UI ให้เปิดหน้าเว็บลองใช้ และดูว่าหน้าจอแสดงผลถูกต้องด้วย

พอมีวิธีตรวจ agent ก็ทำงาน รันตรวจ อ่านข้อผิดพลาด แล้วแก้ต่อเองได้ คนไม่ต้องกลับมาตรวจเรื่องพื้นฐานทุกข้อหลังจากมันบอกว่าเสร็จแล้ว

ตัวอย่างที่ผู้เขียนยกจาก Claude Code มีหลายแบบ:

- สั่งให้รัน auth tests หลังแก้โค้ด และแก้ต่อจนผ่าน
- ใช้ `/goal` ให้ model อีกตัวตรวจเงื่อนไขหลังแต่ละรอบ
- ใช้ Stop hook ซึ่งเป็นคำสั่งที่รันเมื่อ agent กำลังจะหยุด เพื่อไม่ให้ agent หยุดทั้งที่ typecheck ยังไม่ผ่าน
- ใช้ `/code-review` ส่ง diff ให้ agent อีกตัวตรวจ โดยตัวตรวจไม่ได้เห็นบทสนทนาที่ใช้เขียนโค้ด

ควรระบุด้วยว่าจะให้ review อะไร เช่น ตรวจว่าโปรแกรมทำงานถูกต้อง ไม่ต้องวิจารณ์สไตล์โค้ด วิธีนี้ช่วยลดงานตรวจที่คนต้องทำซ้ำ แต่คนยังต้องอ่านหลักฐานและตัดสินเรื่องที่ test ไม่ครอบคลุม ดู [[agentic-code-review|การตรวจโค้ดที่ agent เขียน]]

## บอกเป้าหมายและข้อจำกัดที่อ่านจากโค้ดไม่ได้

Agent เปิด repo ดูโครงสร้างไฟล์และวิธีรัน test เองได้ แต่โค้ดไม่บอกว่าที่ประชุมตกลงอะไร ทำไมงานนี้ถึงสำคัญ หรือมีอะไรที่ห้ามเปลี่ยน สิ่งเหล่านี้คือข้อมูลที่คนมอบหมายต้องบอก

ตัวอย่างในบทความ แทนที่จะขอให้ dashboard เร็วขึ้นเฉย ๆ ให้ระบุว่า:

- หน้า `/team` ขององค์กรที่มีสมาชิกเกิน 10,000 คน ต้องโหลดที่ p95 ต่ำกว่า 2 วินาที p95 หมายถึง 95% ของครั้งที่วัดโหลดเสร็จภายในเวลานั้น
- เหตุผลคือผู้ดูแลองค์กรเปิดหน้านี้ทุกวัน และเรื่องโหลดช้าเป็นปัญหาที่แจ้งเข้ามาบ่อย
- ห้ามเปลี่ยน schema ฐานข้อมูลหรือรูปแบบคำตอบของ API
- ไม่รวมการแก้ UI หรือ cache ทั้งหน้า
- รัน `scripts/perf/team.sh` แล้วแสดงค่าก่อนและหลังแก้

ตัวเลขนี้เป็นตัวอย่างคำสั่งงาน ไม่ใช่ผลทดสอบที่ผู้เขียนรายงาน ถ้ายังอยู่ช่วงสำรวจ ก็เริ่มด้วยคำถามกว้าง ๆ ได้ หรือให้ agent ถามจนช่วยเขียน spec ได้ แล้วใช้ spec นั้นตรวจงานภายหลัง

คนจึงบอกผลที่ต้องการและข้อจำกัดให้ครบ ส่วนวิธีแก้โค้ดปล่อยให้ agent เสนอจากสิ่งที่มันอ่านพบ

## ถ้าต้องแก้เรื่องเดิมซ้ำ ให้จดคำแนะนำไว้ให้ทั้งทีม

ถ้าเราต้องเตือนเรื่องเดิมมากกว่าหนึ่งครั้ง Addy แนะนำให้เขียนไว้ใน `CLAUDE.md` ซึ่งเป็นไฟล์คำแนะนำที่ Claude Code อ่านตอนเริ่มงาน หรือทำเป็น skill สำหรับขั้นตอนที่ใช้ซ้ำ อย่าปล่อยให้บทเรียนอยู่แค่ในบทสนทนาหรือเครื่องของคนคนเดียว

สิ่งที่ควรจดคือคำสั่งตรวจงาน จุดในโค้ดที่ทำให้เข้าใจผิดง่าย เหตุผลของการตัดสินใจที่หาใน repo ไม่เจอ และข้อผิดพลาดที่ต้องแก้ซ้ำ ควรเขียนสั้น ๆ แล้วกลับมาดูด้วยว่า model รุ่นใหม่ยังต้องใช้คำเตือนนั้นหรือไม่

การแก้ครั้งนี้จึงช่วยงานครั้งหน้าได้ด้วย แนวคิดนี้เชื่อมกับ [[harness-ratchet|การนำข้อผิดพลาดมาปรับคำแนะนำหรือเครื่องมือตรวจให้ไม่พลาดซ้ำ]]

## ใช้เครื่องมือบังคับเฉพาะข้อห้ามและขั้นตอนที่ข้ามไม่ได้

Addy แยกคำแนะนำที่ให้ model อ่าน ออกจากข้อจำกัดที่โปรแกรมบังคับ คำสั่งใน prompt, `CLAUDE.md` และ skill อาศัยให้ model ทำตาม ส่วน hook, กฎห้ามใช้เครื่องมือ และการตั้งค่าที่องค์กรควบคุม ใช้กำหนดข้อจำกัดนอกข้อความที่ส่งให้ model

ตัวอย่างเช่น ถ้าห้ามแก้ไฟล์ generated client หรือจำเป็นต้องรันสคริปต์ตรวจ license header ทุกครั้ง ก็ควรมีเครื่องมือตรวจหรือบล็อกจริง ๆ แต่ความชอบเล็กน้อยไม่จำเป็นต้องกลายเป็น hook ทุกข้อ เพราะอาจทำให้ agent ทำงานยุ่งยากโดยไม่ได้ช่วยให้ผลดีขึ้น

เขาอ้างแนวคิดของ Andy Grove จากหนังสือ *High Output Management* ว่าควรดูจากผลงานในงานชนิดนั้น แล้วค่อยตัดสินใจว่าจะกำกับใกล้ชิดแค่ไหน ไม่ใช่ใช้วิธีเดียวกับทุกงาน และเมื่อเปลี่ยน model ก็ควรทบทวนกฎเก่า ไม่เพิ่มคำเน้นหรือตัวพิมพ์ใหญ่ไปเรื่อย ๆ

ข้อแนะนำนี้ไม่ได้รับรองว่า hook หรือระบบอนุญาตใดป้องกันความผิดพลาดได้ทั้งหมด แต่ช่วยให้แยกออกว่าเรื่องไหนแค่แนะนำ และเรื่องไหนต้องบังคับด้วยระบบ

## ตรวจแผนก่อนเขียนโค้ด และแบ่งงานไม่ให้หลาย agent ทำซ้ำกัน

ก่อนเริ่มงานใหญ่ ให้ agent เสนอแผนแล้วอ่านว่ามันตั้งสมมติฐานอะไรไว้ ถ้าเข้าใจ requirement ผิด แก้ตอนนี้ง่ายกว่ารอจนเขียนโค้ดเสร็จ จะให้ agent อีกตัวเริ่มจากบทสนทนาใหม่มาตรวจแผนก็ได้

ผู้เขียนยก `/batch` ใน Claude Code ซึ่งแบ่งงานแก้โค้ดแบบซ้ำ ๆ เป็น 5 ถึง 30 งาน แล้วให้แต่ละงานใช้ [[git-worktrees|worktree]] หรือสำเนา checkout แยกกัน พร้อมสร้าง pull request หรือ PR แยกแต่ละงาน คนยังต้องตรวจว่างานเหล่านั้นซ้ำกันหรือไม่ และทำส่วนที่ทุกงานต้องใช้ร่วมกัน เช่น interface ให้พร้อมก่อน

การแยก worktree กันไม่ให้เขียนทับไฟล์ใน working directory เดียวกัน แต่ไม่ได้ช่วยถ้าแต่ละ agent ออกแบบ interface ที่ต้องใช้ร่วมกันคนละแบบ จึงต้องแบ่งความรับผิดชอบให้ชัดตั้งแต่แผน

## อธิบายใหม่สองครั้งแล้วยังเข้าใจผิด ให้เริ่ม session ใหม่

Addy แนะนำให้ดูช่วงแรกว่า agent เข้าใจงานถูกไหม ถ้าเห็นว่ากำลังทำผิดเรื่อง ให้หยุดและแก้ทันที ถ้าอธิบายใหม่สองครั้งแล้ว agent ยังเข้าใจผิด ก็ควรเริ่ม session ใหม่ โดยแก้คำขอให้ชัดจากสิ่งที่เพิ่งพบ

การต่อบทสนทนาเดิมไปเรื่อย ๆ ทำให้ model ต้องอ่านทั้งคำสั่งที่เปลี่ยนและวิธีที่ลองพลาดแล้ว ผู้เขียนยังยก `/rewind` สำหรับย้อนโค้ดและบทสนทนาไปลองใหม่จากจุดก่อนหน้า

เป้าหมายคือแก้ความเข้าใจผิดตั้งแต่ต้น ไม่ใช้เวลาทั้งวันคอยแก้ผลลัพธ์จากคำขอที่ยังคลุมเครือ

## ให้ agent ทำงานได้ แต่คนยังต้องตัดสินใจว่าจะนำอะไรไปใช้

Test ผ่านไม่ได้แปลว่าฟีเจอร์นั้นควรมี Addy เล่าว่าเขาเคยให้ agent หาว่าผลิตภัณฑ์ขาดอะไรเมื่อเทียบกับคู่แข่ง แล้วทำ PR มาให้ เขาอ่านผลค้นคว้าและดูโค้ดผ่าน ๆ จนเกือบอนุมัติงานที่เพิ่มความซับซ้อนให้ผู้ใช้ แต่ให้ประโยชน์น้อย

Agent จึงช่วยเขียนโค้ด แก้ข้อผิดพลาดที่ linter พบ เขียน unit test และแก้โค้ดตามความเห็นจาก review ได้ ส่วนคนยังต้องตัดสินใจเรื่องผลิตภัณฑ์ ความปลอดภัย ข้อกำหนดที่ต้องปฏิบัติตาม และจะปล่อยงานไหนให้ผู้ใช้จริง การอ่าน diff ต้องเข้าใจพอจะรับผิดชอบได้เมื่อระบบมีปัญหา ไม่ใช่อ่านแค่ชื่อฟังก์ชันแล้วกดผ่านเพราะ test เป็นสีเขียว

คนไม่จำเป็นต้องตามทุกขั้นที่ agent ทำ แต่ควรกำหนดข้อจำกัด เลือกว่าจะตรวจส่วนไหน เก็บหลักฐานอะไร และงานแบบใดต้องให้คนอนุมัติ การแบ่งงานให้แต่ละ diff เล็กพออ่านเข้าใจก็ช่วยให้ตรวจได้จริง เรื่องนี้ต่อจาก [[critical-thinking-when-agents-do-the-work-osmani|บทความที่เตือนให้คนยังคิดและตัดสินใจเอง แม้จะให้ agent ทำงานแทน]]

## ก่อนปล่อยให้ทำงานเอง ต้องบอกว่าจะหยุดเมื่อไรและทำอะไรได้บ้าง

การเปิด agent ทิ้งไว้ข้ามคืนไม่ได้ช่วย ถ้ามันเข้าใจงานผิดตั้งแต่ต้น Addy เสนอให้ตอบห้าข้อนี้ก่อนเริ่มงานที่ไม่มีคนคอยเฝ้า:

1. **งานเสร็จเมื่อไร?** เช่น ทำตาม spec ครบ หรือแก้โค้ดจน test ที่ระบุผ่าน
2. **Agent ตรวจเองอย่างไร?** ระบุชุด test คำสั่งตรวจ หรือขั้นตอน review
3. **Agent ทำอะไรได้บ้าง?** ระบุเครื่องมือที่ใช้ได้ ข้อจำกัดของ sandbox ที่ใช้รันงาน ตำแหน่ง worktree และ branch ที่อนุญาตให้ push
4. **ทำต่อได้นานหรือใช้เงินเท่าไร?** จำกัดจำนวนรอบหรืองบประมาณ
5. **ส่งผลไว้ที่ไหน และเรื่องไหนต้องรอคนอนุมัติ?** เช่น เปิด PR ส่งสรุป หรือหยุดก่อนทำสิ่งที่ย้อนกลับไม่ได้

ก่อนใช้กับงานจำนวนมาก เขาแนะนำให้ลองกับสามไฟล์ก่อน ปรับคำสั่งจนได้ผล แล้วค่อยทำที่เหลือ งานชนิดใหม่ก็ควรดูการรันช่วงแรก ๆ ก่อนเชื่อใจให้ทำเอง

คนจึงไม่ต้องเฝ้าทุกขั้น แต่ยังรู้ว่า agent จะหยุดตรงไหนและจะเรียกให้เราตัดสินใจเมื่อไร ดู [[loop-engineering|การออกแบบขั้นตอนทำงานและตรวจซ้ำ]] กับ [[long-running-agents|agent ที่ทำงานต่อเนื่องเป็นเวลานาน]]

## ก่อนเปิด agent เพิ่ม ให้แต่ละตัวรัน test และให้ agent อีกตัวตรวจ

Addy บอกว่าปกติเขาใช้ agent เบื้องหลังสี่ถึงห้าตัว พร้อมกับ session ในเครื่องอีกบางส่วน และบางวันก็ยังมากเกินไป ยิ่งเปิดหลายตัว งานติดตามและ review ก็ยิ่งเพิ่ม ปัญหานี้คือ [[orchestration-tax|เวลาที่เสียไปกับการประสานและตรวจงานจากหลาย agent]]

เขาเสนอให้ agent รัน test หรือคำสั่งตรวจที่กำหนดไว้ แล้วให้ agent อีกตัวตรวจผลงานโดยไม่เห็นบทสนทนาที่ใช้เขียนโค้ด เมื่อมีเรื่องต้องให้คนตัดสินใจจึงค่อยแจ้งเตือน คนไม่ต้องเปิดเช็กทุก session ว่าทำถึงไหนแล้ว และมีเวลาอ่านงานสำคัญมากขึ้น

ตัวชี้วัดก็ควรดูทั้งความเร็วและคุณภาพ เช่น PR แต่ละงานใช้เวลาตรวจและแก้จน merge นานเท่าไร ต้อง revert หรือแก้งานใหม่บ่อยไหม ถ้านับจำนวน PR ที่ merge ก็ควรดูจำนวนงานที่ต้องย้อนกลับด้วย ไม่ใช้สัดส่วนโค้ดที่ AI เขียนเป็นเป้าหมายหลัก

จำนวน agent ที่เหมาะสมจึงขึ้นกับว่าเราตรวจผลงานได้ทันแค่ไหน ไม่ใช่ว่าเปิดพร้อมกันได้กี่ตัว

## อย่าเริ่มทุกงานเพียงเพราะให้ agent ทำได้เร็ว

แม้สร้าง PR ได้เร็ว ทีมก็ยังต้องอ่าน ตรวจความปลอดภัย ตอบปัญหาผู้ใช้ และดูแลโค้ดนั้นต่อ Addy จึงแนะนำให้จำกัดงานที่ทำค้างไว้ และถามก่อนเริ่มว่าใครต้องการงานนี้ จะวัดว่าช่วยเขาได้อย่างไร และถ้าผลไม่ดีจะหยุดเมื่อไร

การปฏิเสธงานที่ไม่คุ้มยังเป็นหน้าที่ของคน การใช้เวลาสร้างน้อยลงไม่ได้ทำให้ภาระดูแลหลังปล่อยใช้งานหายไปด้วย

## คุม agent ได้ ไม่ได้แปลว่าคุมทีมคนได้

ผู้เขียนเตือนว่าการเทียบกับงานผู้จัดการมีข้อจำกัด:

- **ทีมคนต้องการทักษะจัดการอีกหลายอย่าง:** ผู้จัดการยังต้องสร้างแรงจูงใจ แก้ความขัดแย้ง ช่วยพัฒนาอาชีพ และสร้างความไว้ใจกับลูกทีม การเปิด agent ห้าตัวไม่ได้ฝึกทักษะเหล่านี้
- **ให้ agent ลองหลายวิธีได้ง่ายกว่าให้คนทำ:** ผู้เขียนมองว่าการทำใหม่มีต้นทุนต่ำ จึงให้ลองสร้างสองหรือสามทางแล้วเปรียบเทียบได้ แต่ยังต้องมีคนอ่านและตัดสินผล
- **บันทึกในเครื่องเราไม่ได้ส่งต่อให้เพื่อนร่วมทีมอัตโนมัติ:** เขายก auto memory ที่เก็บบันทึกไว้ในเครื่องเดียว จึงควรเขียนคำแนะนำไว้ในที่ที่ทีมใช้ร่วมกัน และไม่ถือว่าบันทึกเหล่านี้แทนประสบการณ์และวิจารณญาณของคนได้
- **Agent อาจทำตามทั้งที่คำขอมีปัญหา:** ผู้ใช้ก็อาจเชื่อคำตอบที่ดูมั่นใจง่ายเกินไป เขาอ้างงานวิจัย Wharton เรื่อง [[cognitive-surrender|การยอมรับคำตอบ AI โดยไม่ตรวจเอง]] และเสนอให้ลองขอข้อโต้แย้งต่อคำตอบนั้นด้วย
- **หลายตัวอาจพลาดเหมือนกัน:** ถ้าใช้ model เดียวกัน จุดแข็งและจุดอ่อนก็อาจเหมือนกัน การเปิดหลาย session จึงไม่เท่ากับได้คนหลายความถนัด และต้องประเมินใหม่เมื่อเปลี่ยน model
- **นักพัฒนาที่เพิ่งเริ่มงานยังต้องได้ฝึก:** ถ้า agent ทำงานพื้นฐานแทนหมด ทีมต้องจัดโอกาสให้ junior developer ฝึกและเข้าใจงานด้วย
- **ยังต้องมีเวลาให้เพื่อนร่วมทีม:** อย่าให้การสั่งและตรวจ agent ทั้งวันเบียดเวลาคุย ประสานงาน และช่วยคนในทีม

Addy สรุปว่าทักษะเหล่านี้ฝึกได้โดยไม่ต้องเปลี่ยนตำแหน่ง เริ่มจากสั่งงานให้ชัด เตรียมวิธีตรวจ และอ่านผลงานอย่างรับผิดชอบ ดูแนวทางนำไปใช้ใน [[managing-coding-agents|การมอบหมายและตรวจงานจาก coding agent]]
