# Your Coding Agents Made You a Manager / พอใช้ coding agent ทั้งวัน เราก็ทำงานแบบผู้จัดการแล้ว

[[addy-osmani|Addy Osmani]] ผู้เขียนเรื่องระบบรอบ AI agent และตอนนี้ทำงานกับ Claude Code ที่ Anthropic บอกว่า ทักษะจัดการ agent ใกล้กับทักษะจัดการทีมมาก และไม่ต้องมีตำแหน่งผู้จัดการก็ฝึกได้

ถ้าเราใช้ coding agent ทั้งวัน เราก็กำลังจัดการอยู่แล้ว เราเลือกงาน เขียนคำสั่ง มอบหมาย ติดตามผล ประเมินของที่ได้ แล้วตัดสินว่าอะไรจะออก คนที่ได้ผลดีจาก agent ไม่จำเป็นต้องเก่ง prompt ที่สุด แต่เป็นคนที่เรียนรู้การจัดการ ไม่ว่าจะตั้งใจฝึกหรือไม่

เขาไม่ได้ชวนให้ IC ไปเป็นผู้จัดการที่จมอยู่ในปฏิทิน คำว่า management ในบทนี้มีความหมายแคบกว่านั้น คือทำให้ผลงานดีขึ้นด้วยการเปิดทางให้งานของคนอื่นเดินได้ และเขาไม่ได้บอกว่า agent มาแทนผู้จัดการหรือเพื่อนร่วมงานได้

เรื่องที่เราบ่นเรื่องผู้จัดการแย่ เขาชวนให้มองเป็น bug report สำหรับวิธีคุยกับ agent โดยเฉพาะการส่งงานที่คลุมเครือ ขาดบริบท หรือเป้าเลื่อนไปเรื่อย ๆ คนที่เคยรับงานแบบนั้นมาหลายปี อาจรู้ดีอยู่แล้วว่างานที่ส่งต่อกันดีมีหน้าตาอย่างไร

เขาย้ำว่าเคยเขียนไว้แล้วว่า [coding agent ต้องการผู้จัดการ](https://addyosmani.com/blog/coding-agents-manager/) และเคยเขียนเรื่อง [[cognitive-surrender|cognitive surrender]] บทนี้เอาวิธีของ engineering manager ที่ดี มาเทียบกับสิ่งที่ได้จากการใช้และสร้าง Claude Code โดยเรียงหัวข้อตาม impact

## ให้มันมีวิธีตรวจงานเอง

วิธีที่ดีคือให้ agent มีกลไกตรวจงาน เช่น ชุด test, การ build หรือภาพหน้าจอ แล้วให้มันโชว์ผลนั้นเป็นหลักฐาน วิธีที่พลาดคือเชื่อแค่ว่า "ดูเหมือนเสร็จแล้ว" เพราะงั้นเราจะกลายเป็นชุด test ของมันเอง

ผู้จัดการที่มีประสบการณ์มั่นใจงานทีมได้โดยไม่ต้องอ่านทุกอย่าง เพราะมีราวกั้นอย่าง CI, code review, dashboard และ on-call คนที่ไม่มีราวกั้นจะตรวจทุกอย่างเอง แล้วกลายเป็นคอขวดในไม่กี่เดือน Agent ก็เหมือนกัน คู่มือ best practices ของ Claude Code อธิบายว่า agent หยุดเมื่องานดูเสร็จ ถ้าไม่มีตัวตรวจ "ดูเสร็จ" ก็คือตัวตรวจเดียวที่มี พอมีตัวตรวจ มันทำงาน รันตัวตรวจ เห็นที่พัง แล้วแก้เองได้ เช่น เปิดหน้า UI ในเบราว์เซอร์แล้ววนจนกว่าจะใช้ได้และดูดี

ตัวตรวจจะเป็นอะไรก็ได้ ขอให้ให้ผลผ่านหรือไม่ผ่านชัด เช่น test, exit code ของการ build, linter, สคริปต์เทียบ diff และภาพหน้าจอ คู่มือบอกว่าบรรทัดที่มีประโยชน์ที่สุดใน `CLAUDE.md` คือคำสั่งที่รันการตรวจพวกนี้ แล้วค่อยดึงมันเข้า workflow ได้หลายทาง

- **Ask.** สั่งแบบ "รัน auth tests หลังทำ แล้วทำต่อจนกว่าจะผ่าน"
- **Set a goal.** คำสั่ง `/goal` ให้ model อีกตัวเช็กเงื่อนไขหลังทุก turn เหมาะกับงานพื้นหลังที่ยาว
- **Enforce.** Stop hook กันไม่ให้จบ turn จนกว่า typecheck จะผ่าน
- **Have it reviewed.** `/code-review` ส่ง diff ให้ subagent ที่ไม่ได้เห็นบทสนทนานี้ เหมือนคนเขียน PR ไม่ควรอนุมัติงานตัวเอง

ขอบเขตการ review ก็กำหนดได้ ถ้าขอให้หาปัญหา มันจะหาอะไรสักอย่างเสมอ แต่ถ้าขอให้หาเรื่องความถูกต้องแล้วข้ามสไตล์ มันจะทำแบบนั้น Skills, hooks, subagents และ MCP ในเครื่องมือ Claude Code มีไว้เชื่อมช่องว่างระหว่างการทำงานกับการตรวจงาน เพื่อให้เราโฟกัสแค่เรื่องที่มันตรวจเองไม่ได้

**สิ่งที่ช่วยได้:** เราไม่ต้องเป็นชุด test ของ agent แต่ยังดูเรื่องที่ตัวตรวจจับไม่ได้

## ใส่บริบทที่มันอ่านจาก repo ไม่ได้

วิธีที่ดีคือสรุปสิ่งที่ agent จะไม่รู้แม้เปิดดู repo แล้ว ได้แก่ เป้าของงาน ทำไมสำคัญ ข้อจำกัด อะไรไม่อยู่ในงานนี้ และเกณฑ์ว่าเสร็จเมื่อไร วิธีที่พลาดคือส่งงานประโยคเดียวแล้วเก็บความคาดหวังไว้ในหัว หรือยัดรายละเอียดที่มันอ่านจากโค้ดได้เอง

ผู้จัดการที่ส่งงานเก่งบอกผลที่ต้องการ ข้อจำกัด และเป้า แล้วปล่อยให้คนทำเลือกวิธีเอง ทหารเรียกแนวนี้ว่า commander's intent ที่ Netflix เรียกว่า "context, not control"

งานยากคือไม่รู้ว่า agent ขาดบริบทอะไร ปกติมันเริ่มด้วยการอ่านโค้ด และ model ตอนนี้จับโครงสร้างโฟลเดอร์ ข้อตกลงในโปรเจกต์ และวิธีรัน test ได้เร็วกว่าที่เราอธิบาย สิ่งที่ควรเขียนจึงเป็นเรื่องที่ไม่อยู่ใน repo เช่น มติจากประชุม ขั้นตอน deploy ภายใน ทำไมงานนี้สำคัญ และครั้งนี้ถือว่าเสร็จเมื่อไร

เขายกตัวอย่างงานคลุมเครืออย่าง "make the dashboard faster" แล้วแปลงเป็น prompt ประมาณนี้ ตัวเลขเป็นแค่ตัวอย่าง

> Get p95 load time for the /team dashboard under 2s for orgs with 10k+ members.
>
> Why: enterprise admins open it daily, and slow loads are their top support ticket.
>
> Constraints: no schema changes; keep the API response shape.
>
> Out of scope: UI changes; caching the whole page.
> Check: run scripts/perf/team.sh and show before and after numbers.

งานสำรวจยังเขียน prompt กว้าง ๆ แล้วค่อยปรับไปได้ ถ้ายังเขียน prompt ไม่พร้อม ให้ agent สัมภาษณ์เราจนกว่าจะเขียน spec ได้ เซฟ spec ไว้ แล้วเปิดเซสชันใหม่ให้สร้างตามนั้น เพื่อเอามาเทียบตอน review ทีหลัง เรื่องเครื่องมือก็เหมือนรับน้องใหม่ ถ้าเป็น CLI ที่มันรู้จักแล้ว เช่น `gh` มักไม่ต้องอธิบายเพิ่ม

**สิ่งที่ช่วยได้:** เราไม่ต้องเล่าทั้ง repo แค่บอกสิ่งที่โค้ดพูดแทนเราไม่ได้

## แก้ซ้ำแล้วให้ความรู้สะสม

ถ้าแก้เรื่องเดิมเกินหนึ่งครั้ง ให้จดใน `CLAUDE.md` ของทีม หรือทำเป็น skill ที่ใช้ด้วยกันได้ แล้วคอยดูว่า model ใหม่ยังต้องการคำแก้พวกนี้ไหม อย่ามาแก้มือซ้ำทุกเซสชัน หรือพึ่งความรู้ที่อยู่แค่เครื่องตัวเอง

ทีมที่ได้ประโยชน์จาก `CLAUDE.md` อัปเดตค่อนข้างบ่อย และจดบทเรียนจากความผิดพลาดที่ไม่อยากเจออีก บางทีมถึงขั้น mention `@claude` ใน code review เพื่อเปลี่ยน feedback เป็นนโยบายถาวร ไฟล์นี้ควรสั้น สิ่งที่ควรอยู่ในนั้นคือ

- วิธีตรวจอะไรสักอย่าง พร้อมคำสั่งจริง
- จุดในโค้ดที่ทำให้เข้าใจผิดง่าย
- การตัดสินใจที่ไม่มีใน repo
- เรื่องที่เราแก้ไปแล้วสองครั้ง

งานเขียนแบบนี้อยู่นานกว่าคนย้ายทีม และนานกว่า model ถูกเปลี่ยน

**สิ่งที่ช่วยได้:** แต่ละครั้งที่แก้ ไม่จบแค่รอบนั้น แต่กลายเป็นกติกาที่รอบหน้าไม่ต้องสอนใหม่ แนวนี้ใกล้ [[harness-ratchet]]

## ให้มันตัดสินใจเอง บังคับเฉพาะเรื่องที่งอไม่ได้

ให้ agent เลือกทางเป็นปกติ แล้วใช้การบังคับแข็งอย่าง hook หรือ deny rule เฉพาะเรื่องที่ต้องเกิดเสมอหรือห้ามเกิดเด็ดขาด อย่าเขียนกติกาด้วยตัวพิมพ์ใหญ่ทั้งประโยค อย่าทำ hook สำหรับเรื่องที่แค่ชอบ และอย่าถือนิสัยจาก model เก่าไว้ทั้งที่ model ใหม่ไม่ต้องการแล้ว

Addy อ้างหนังสือ *High Output Management* ของ Andy Grove เรื่อง task-relevant maturity คือระดับการดูแลควรขึ้นกับผลงานในงานชิ้นนั้น ไม่ใช่ความสามารถรวม ๆ คำแนะนำเก่าสำหรับผู้จัดการใหม่ก็ไปทางเดียวกัน คือให้พื้นที่มากกว่าที่เราสบายใจนิดหน่อย แล้วคอยหนุนพร้อมกับถามผล

ใน Claude Code สิ่งที่เป็นคำขอคือ prompt, `CLAUDE.md` และ skill เพราะ model พิจารณาแล้วเลือกทำได้ ส่วน hook, deny rule และ managed settings คือข้อบังคับที่ต้องทำเสมอ ส่วนใหญ่ควรให้ agent ตัดสินเอง เพราะมันเห็นโค้ดจริง อาจรู้ได้ดีกว่าเราก่อนเริ่ม ว่าแนวทางนี้เข้ากับงานหรือไม่ สิ่งที่ควรบังคับเช่น "ห้ามแก้ generated client" หรือ "ต้องรันสคริปต์ license header เสมอ" เซสชันใหม่ในเทอร์มินัลและ VS Code เริ่มที่ auto mode และมีตัวกรองกันพฤติกรรมอันตรายอย่าง deploy ขึ้น production หรือ force push ทับงานคนอื่น

ถ้าเน้นบรรทัดใน `CLAUDE.md` แล้วยังไม่ทำตาม บรรทัดนั้นควรเป็น hook ถ้า hook แค่บอกความชอบ ควรถอดออก คู่มือยังมีรายการนิสัยที่เลิกได้แล้ว เช่น สั่งด้วยตัวพิมพ์ใหญ่ทั้งประโยค, คำว่า "think harder" เพราะตอนนี้ปรับความพยายามเป็นการตั้งค่าแล้ว และ "don't be lazy" กับ model ปัจจุบัน สิ่งพวกนี้มักทำให้มีกฎมากเกินและทำงานเกินจำเป็น สำหรับ agent การวางกระบวนการมากเกินไป คือการจุกจิกแบบใหม่

**สิ่งที่ช่วยได้:** เรากำหนดรั้วเฉพาะเรื่องที่พังแล้วเสียหายจริง แล้วปล่อยให้มันเลือกทางในรั้วนั้น

## วางแผนก่อนให้สร้าง

ตกลงแผนก่อนให้เขียนโค้ด อ่านสมมติฐานที่ซ่อนอยู่ แล้วแยกงานขนานไม่ให้ทับกัน อย่าปล่อยให้หลาย agent ทำงานทับกัน แล้วไปเสียบ่ายแก้ merge conflict และตัดสินใจซ้ำ

workflow ที่เขาแนะนำคือเข้า plan mode แล้ววนแก้แผนจนถูก แล้วค่อยมอบหมายให้เขียนโค้ด แผนดี ๆ model มักสร้างได้ในรอบเดียว งานใหญ่ให้เปิดเซสชันที่สองมาดูแผนแบบ staff engineer คือทำ design review ซึ่งเป็นจุดถูกที่สุดที่จะจับทางผิด ตอนอ่านแผนให้หาสมมติฐานที่ยังไม่ชัด เหมือนใน one-on-one ที่ถามว่า "ตรงไหนที่ยังไม่ชัวร์"

การหั่นงานก็เริ่มยกให้ agent มากขึ้น คำสั่ง `/batch` ใน Claude Code เอางานกลไกก้อนใหญ่มาแบ่งเป็น 5 ถึง 30 ชิ้น โชว์แผน แล้วรันใน [[git-worktrees|worktree]] คนละอัน พร้อมเปิด PR คนละใบ เราไม่ต้องหั่นงานเองแล้ว แต่ต้องดูว่าชิ้นงานทับกันไหม และให้ interface ที่ใช้ร่วมกันลงก่อน ถ้าไม่ดูจุดนี้ การเปิดห้าตัวพร้อมกันจะไม่ได้งานห้าเท่า แต่ได้ merge conflict ที่มีคนเขียนห้าคน

**สิ่งที่ช่วยได้:** ความขนานที่ได้ผลมาจากการแยกงานไม่ทับกัน ไม่ใช่จากการเปิดเซสชันเพิ่มอย่างเดียว

## ดึงพวงมาลัยเร็ว แล้วเริ่มใหม่เร็ว

ดูนาทีแรกแล้วดึงทางทันที พอเห็นว่าหลุดทางให้แก้เลย ถ้าแก้ไปแล้วสองครั้งแล้วยังไม่เข้าที่ ให้เปิดเซสชันใหม่ด้วย prompt ที่ดีขึ้น อย่าพยายามแก้รอบที่สามหรือสี่ทั้งที่ควรแก้คำขอ

ผู้จัดการที่มีประสบการณ์รู้ว่า ถ้าคนเก่งพลาดซ้ำ ๆ ปัญหาอาจอยู่ที่คำสั่ง บริบท หรือขอบเขตงาน เวอร์ชันของ agent คือ พอหลุดทางให้กด Esc แล้วถ้าแก้สองครั้งแล้วยังไม่ไหว ให้เคลียร์เซสชันแล้วเขียน prompt ใหม่โดยใส่บทเรียนที่ได้ รอบที่สามส่วนใหญ่แค่เพิ่มข้อมูลที่ model ต้องอ่านซ้ำ รวมทั้งรอบที่พลาดแล้ว

การย้อนกลับที่ถูกก็เปลี่ยนเกม คำสั่ง `/rewind` ย้อนทั้งโค้ดและบทสนทนาไปจุดก่อนหน้า จึงลองทางที่ทะเยอทะยานก่อนได้โดยเสี่ยงน้อย ผู้จัดการที่ดีทำแบบนี้กับคนเหมือนกัน ถ้ายกเลิกความผิดพลาดได้ถูก ก็ให้ลองทางใหญ่ก่อน แล้วค่อยทบทวนและเขียนสิ่งที่ได้ลง `CLAUDE.md` ถ้าใช้ต่อได้

**สิ่งที่ช่วยได้:** เราไม่จมกับการดึงรอบที่พังอยู่แล้ว แต่เริ่มใหม่ด้วยคำขอที่ชัดขึ้น

## มอบหมายงาน แต่อย่ามอบหมายการตัดสินใจ

ให้ agent ทำงาน ส่วนเรื่องสำคัญยังเป็นของเรา เช่น ทิศทางสินค้า เส้นเขต security และอะไรจะออก ดูทุก diff เหมือนเราจะโดนเรียกตอนดึกถ้ามันพัง อย่าอนุมัติ diff ใหญ่เพียงเพราะ test เขียวและชื่อดูสมเหตุสมผล นั่นไม่ใช่ code review แต่เป็นการรับรองโค้ด

ไม่มีผู้จัดการคนไหนจะพูดได้ว่า "ลูกทีมส่งออกไป ไม่ใช่ฉัน" กับ agent ก็เช่นกัน Addy เล่าว่าตัวเองเกือบทันกับกับดักนี้ เขาให้ agent ไปหาช่องว่างเทียบคู่แข่งแล้วเขียน PR ในเครื่องตัวเองให้ปิดช่องนั้น เขาอ่านงานวิจัย ดูโค้ดผ่าน ๆ แล้วเกือบจะดันการเปลี่ยนแปลงที่เพิ่มความซับซ้อนให้ผู้ใช้โดยได้ประโยชน์น้อย เขามอบหมายงานแล้ว เกือบมอบหมายการตัดสินใจไปด้วย กับดักนี้พบบ่อย คือ diff สัก 600 บรรทัด ชื่อดูดี test เขียว ก็อนุมัติ

งานที่เหมาะกับ agent เช่น สไตล์, lint, งานตามหลัง review, บั๊กทั่วไป และ unit test ส่วนเส้นเขต security, compliance และการตัดสินใจด้านสินค้า ยังเป็นของคน การประสานงานก็เหมือนกัน agent ช่วยตามส่งต่องานได้ แต่การเลือกเมื่อคำขอชนกัน และการทำให้คนยอมรับปาก เป็นงานคน

เราไม่ต้องอยู่ในวงในของทุกการเปลี่ยน สิ่งที่ต้องถือคือวงนอก ได้แก่ ข้อจำกัด เราอ่านผลจริงแค่ไหน เก็บหลักฐานอะไรไว้ และจุดไหนที่คนต้องเซ็นรับ และให้การเปลี่ยนแปลงเล็ก เพราะหน่วยที่ review ได้คือหน่วยที่เข้าใจได้

**สิ่งที่ช่วยได้:** งานเดินต่อได้โดยที่การตัดสินใจสำคัญยังเป็นของคนที่รับผิดชอบระบบ เรื่องนี้เชื่อมกับ [[agentic-code-review]] และ [[critical-thinking-when-agents-do-the-work-osmani]]

## ออกแบบรอบที่เราไม่ต้องเฝ้า

ก่อนปล่อยงานที่ทำเองได้นาน ให้นิยามว่าเสร็จเมื่อไร มีวิธีตรวจเอง มีขอบเขต มีราวกั้น และมีจุดที่คนต้องอนุมัติ อย่าปล่อยโปรเซสยาวข้ามคืนก่อนนอนทั้งที่ยังไม่รู้ว่าเสร็จเมื่อไรหรือจะหยุดเมื่อไร แล้วยืนเช้ามาเจอว่ามันทำทั้งคืนบนสมมติฐานที่ผิด

ผู้จัดการข้ามชั้นไม่จัดการงานวิศวกรทีละคน แต่จัดการเป้า ราวกั้น จุดตรวจ และหัวหน้างาน Agent ก็เดินทางคล้ายกัน มันส่งงานย่อยให้ subagent ได้แล้ว และรันเองตามตาราง หลัง CI พัง หรือหลังมี PR ใหม่ได้ พรมแดนถัดไปคือระบบที่เริ่มเอง ตรวจเอง และเรียกคนเฉพาะตอนต้องตัดสินใจ บทบาทจึงย้ายจากการคุมเซสชันไปเป็นการออกแบบลูป ห้าคำถามก่อนปล่อยงานที่ไม่มีคนเฝ้า คือคำถามเดียวกับที่ผู้จัดการดีถามก่อนมอบโปรเจกต์ให้คนเก่งแล้วไปลาพัก

- มันรู้ไหมว่างานเสร็จหน้าตาอย่างไร เช่น เงื่อนไขเป้า, ไฟล์ spec หรือ test ที่ยังแดงอยู่แล้วต้องทำให้เขียว
- มันมีวิธีตรวจเองไหม เช่น ชุด test, Stop hook หรือขั้น review
- ขอบเขตอยู่ที่ไหน เช่น สิทธิ์, sandbox, worktree หรือ branch ที่อนุญาตให้ push
- ราวกั้นคืออะไร เช่น จำกัดจำนวน turn หรืองบ
- ผลโผล่ที่ไหน และใครอนุมัติ เช่น PR หรือสรุป และคนต้องอนุมัติการกระทำที่ย้อนไม่ได้

คู่มือยังแนะให้ทดลองก่อน เช่น ให้งานชุดใหญ่รันสามไฟล์ก่อน ปรับ prompt แล้วค่อยรันที่เหลือ และดูรอบแรก ๆ ของงานใหม่ก่อนที่จะเชื่อใจให้ทำเอง เหมือนช่วงทดลองงาน

**สิ่งที่ช่วยได้:** งานพื้นหลังเดินได้โดยไม่ต้องมีเราเฝ้าทุก turn แต่ยังมีจุดหยุดและจุดให้คนตัดสินใจ แนวนี้ใกล้ [[loop-engineering]] และ [[long-running-agents]]

## ขยายการตรวจ ไม่ใช่ขยายความใส่ใจ

เพิ่มการใช้ agent เร็วเท่าที่ตัวตรวจ เป้า และผู้ review คนใหม่รับหน้าที่เฝ้าแทนได้ และวัดคุณภาพด้วย ไม่ใช่วัดแค่ปริมาณ อย่าเปิดเซสชันเกินกว่าที่เรา review ได้ดี แล้ววัดความสำเร็จจากปริมาณโค้ดที่ AI เขียน

ผู้จัดการเรียนรู้ span of control ได้ค่อนข้างเร็ว ลูกทีมเกินจุดหนึ่งทุกคนจะได้เวลาน้อยลง คุณภาพก็ตก Agent ก็เหมือนกัน นี่คือ [[orchestration-tax]] ที่เขาเรียกอีกครั้ง คือพ้น agent ไม่กี่ตัว แต่ละตัวถัดไปกินความใส่ใจมากกว่าตัวก่อน วันที่เขาใช้มักมี agent พื้นหลังสี่ถึงห้าตัวบวกเซสชันในเครื่อง และบางวันนั่นก็มากไปแล้ว

การคุมเซสชันจำนวนมากไม่ใช่เรื่องสมาธิเหล็ก แต่เป็นการยกการเฝ้าส่วนใหญ่ให้การตรวจเอง เป้า และผู้ review ที่เริ่มด้วย context ใหม่ แล้วเก็บความใส่ใจไว้กับการตัดสินใจ การแจ้งเตือนดีกว่าการคอยรีเฟรชเอง และควรมองงานพื้นหลังรวมที่จุดเดียว ขยายจำนวน agent ด้วยการเฝ้ามากขึ้นไม่ได้ ขยายได้ด้วยการต้องเฝ้าน้อยลง แล้ววัดระบบ ไม่ใช่วัดความวุ่น ตัวชี้วัดที่มีประโยชน์เช่น เวลาที่ PR ใช้จนจบ เวลาที่คนใหม่เข้าที่ และความถี่ที่ต้อง revert หรือทำใหม่ การวัดร้อยละของโค้ดที่ AI เขียนไม่ใช่เป้าที่มีประโยชน์ เพราะสิ่งที่ต้องการคือคุณภาพและความน่าเชื่อถือ กฎของ Grove ที่ให้วัดคู่กับตัวถ่วงก็ใช้ตรงนี้ ถ้าวัดจำนวน PR ที่ merge ก็ควรวัด revert กับงานที่ต้องทำใหม่ด้วย

**สิ่งที่ช่วยได้:** จำนวนเซสชันไม่ใช่ความสำเร็จ ความสำเร็จคืองานที่ตรวจแล้วรับผิดชอบได้

## ตัดสินใจว่าจะไม่สร้างอะไร

ถามว่าใครต้องการ ของนี้จะรู้ได้อย่างไรว่าได้ผล และอะไรจะทำให้เราหยุด แล้วจำกัดงานที่ทำค้างไว้ อย่าโยนทุกไอเดียที่ฟังขึ้นเข้า PR เพียงเพราะสร้างถูก ของพวกนั้นจะกลายเป็นลิ้นชักขยะที่ทีมต้อง review ดูแลความปลอดภัย และดูแลระยะยาว

คำสำคัญที่ผู้จัดการพูดบ่อยคือ "ไม่" กับ agent การพูดว่าไม่ยากขึ้น เพราะเริ่มงานเกือบฟรี และโยนไอเดียที่ฟังขึ้นเข้า PR ได้ก่อนเที่ยง แต่ทีมยังต้อง review ดูแลความปลอดภัย ซัพพอร์ต และดูแลต่อ ตอนนี้ของขาดคือเวลา review และการตรวจ

คำถามบริหารแบบเก่าจึงสำคัญกว่าเดิม ใครขอมา จะวัดความสำเร็จอย่างไร และจะรู้ได้อย่างไรว่าควรหยุด ถ้าสร้างถูก คำถามยากไม่ใช่ "ทำได้ไหม" แต่เป็น "ควรทำไหม"

**สิ่งที่ช่วยได้:** ของถูกสร้างไม่ได้แปลว่าควรมี คนยังต้องเป็นคนพูดว่าไม่

## จุดที่เปรียบกับผู้จัดการใช้ไม่ได้

เปรียบเทียบนี้มีประโยชน์ แต่ไม่สมบูรณ์ คนที่ใช้แนวนี้เก่งจะรู้ว่าตรงไหนใช้ต่อไม่ได้อย่างไร้เงื่อนไข

- การจัดการคนยากกว่า และทักษะนี้ไม่ได้ถ่ายกลับไป การรัน agent ห้าตัวไม่ได้แปลว่าพร้อมจัดการคนห้าคน ไม่มีสิ่งเทียบเท่าแรงจูงใจ ความขัดแย้ง การเติบโตในอาชีพ หรือความไว้ใจที่สะสมหลายเดือน
- การย้อนงานเกือบฟรี เราถาม agent ได้ในสิ่งที่ไม่ถามคน ถกทางเทคนิคอยู่ที่ไวท์บอร์ดแล้วให้มันสร้างสองสามทางมาเปรียบเทียบได้
- Agent ไม่มีประสบการณ์ มีแต่สมุดโน้ต Auto memory จดบนเครื่องเดียว ไม่ตามไปเซสชันของเพื่อนร่วมงาน และไม่ใช่วิจารณญาณที่คนสะสมทั้งอาชีพ จึงต้องเขียนบทเรียนให้ทั้งทีม
- Agent เต็มใจและมั่นใจ ถ้าสั่งวิศวกรเก่งให้ทำผิด เขาจะเถียงกลับ Agent มักทำตาม และเราเผลอเชื่อมากเกินไป งานวิจัยที่ Wharton เรื่อง cognitive surrender พบว่าผู้ร่วมวิจัยรับคำตอบที่ผิดของ AI เป็นส่วนใหญ่ และยิ่งมั่นใจขึ้นด้วย วิธีต้านคือให้มันโต้แย้งคำตอบของตัวเอง
- เรามีต้นแบบ agent แบบเดียว และมันเปลี่ยนทุกไม่กี่เดือน ทีมคนมีความถนัดต่างกัน แต่ agent ของเรามีจุดแข็งจุดอ่อนชุดเดียวกัน ซึ่งขยับตามแต่ละรุ่นของ model
- ยังต้องฝึก junior developer อยู่ เมื่อ agent รับงานเริ่มต้นที่คนใหม่เคยใช้ฝึกพื้นฐาน เราต้องสร้างรอบฝึกนั้นให้ตั้งใจ
- ทีมคนยังสำคัญ บางวันเราจัดการ agent ทั้งวันโดยไม่ทันคิดว่าไปแย่งเวลาสร้างทีมที่ทำงานด้วยกันได้ อย่าทำแบบนั้น

## ไม่ต้องมีตำแหน่งนี้ก็ได้

ทุ่มแรงกับการทำให้ซอฟต์แวร์ดีเกิดขึ้นจริง ได้แก่ วางบริบท นิยามว่าเสร็จ และ review ให้ดี อย่าวัดตัวเองด้วยจำนวนบรรทัดโค้ด ทั้งที่ปล่อย agent ที่ได้รับโจทย์ไม่ครบและไม่มีคนตรวจ

staff engineer ที่ดีทำแบบนี้มาตลอด พวกเขาเขียนเอกสารออกแบบ วางบริบท review ละเอียด และทำให้คนรอบตัวทำงานได้ดีขึ้น Agent ทำให้วิศวกรทุกคนทำแบบนี้ได้ตั้งแต่วันแรก และเป็นคอร์สเร่งเรื่องการจัดการ ผลกลับมาในนาที ไม่ใช่ในไตรมาส และเรายกเลิกความผิดพลาดของตัวเองได้ งานจึงน้อยลงเรื่องการเขียนโค้ดเอง แล้วมากขึ้นเรื่องการเป็นเหตุให้งานดีถูกเขียนขึ้น

ไม่มีใครเกิดมาเป็นผู้จัดการเก่ง หรือวิศวกรเก่ง ทักษะสร้างด้วยการฝึกเหมือนเดิม แต่กับ agent การฝึกถูก

สิ่งที่เขาชวนให้ลอง

- ทุกงานต้องมีตัวตรวจที่มันรันได้ แล้วขอหลักฐาน
- บอกสิ่งที่มันมองไม่เห็น และไม่ต้องเล่าสิ่งที่มันเห็นได้
- คุยแผนก่อนลงมือเขียนโค้ด
- แก้ซ้ำสองครั้งแล้ว จดใน `CLAUDE.md` งานที่ทำซ้ำบ่อย ทำให้เป็น skill
- แก้ไม่เข้าสักสองครั้ง ให้เริ่มใหม่แล้วเขียนคำขอใหม่
- ดู diff เหมือนเราจะโดนเรียกถ้ามันพัง

เราไม่ต้องอยากเป็นผู้จัดการ แต่วิศวกรที่ใช้ agent ได้ผล จะได้เรียนรู้การจัดการไปพร้อมกัน
