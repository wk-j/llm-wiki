# Critical Thinking When Agents Do the Work / ให้ agent ทำงานแทน แล้วเรายังคิดเองอยู่ไหม

[[addy-osmani|Addy Osmani]] ผู้เขียนเรื่องการพัฒนาซอฟต์แวร์และ AI agent ตั้งข้อสังเกตว่า ยิ่ง AI ทำงานเก่งขึ้น เรากลับยิ่งมีเหตุให้หยุดคิดน้อยลง คำตอบมาเร็ว เขียนดี และส่วนใหญ่ก็ดูถูกต้อง จนเราอ่านผ่าน ๆ แล้วไปทำเรื่องถัดไป ทั้งที่ยังไม่ได้ถามตัวเองเลยว่าเห็นด้วยเพราะอะไร

เขาเองใช้ agent ทำงานหลายอย่างพร้อมกัน และยังอยากใช้ต่อ ประเด็นของบทความนี้คือ เมื่อขั้นตอนทำงานแทบไม่บังคับให้เราคิดเองแล้ว เราจะรักษานิสัยตั้งคำถามและตรวจสอบไว้ได้อย่างไร

## เริ่มจากให้ช่วยทำ จนกลายเป็นเชื่อตามหมด

Addy ชวนสังเกตว่าเวลาใช้ AI เรากำลังอยู่ตรงไหนในสามขั้นนี้

- **Cognitive offloading — ให้ช่วยทำงาน:** เราฝากงานให้ AI แต่ยังตรวจผลและรับผิดชอบสิ่งที่ได้
- **Deferral — เริ่มถือว่าคำตอบถูกแล้ว:** เราเอาคำตอบไปใช้ต่อโดยไม่ได้เผื่อไว้ว่ามันอาจผิด
- **[[cognitive-surrender|Cognitive surrender]] — เลิกคิดตรวจเอง:** คำตอบของ AI กลายเป็นความเห็นของเราไปแล้ว จนไม่รู้สึกว่าต้องตรวจอีก Addy ระบุว่า Steven Shaw และ Gideon Nave จาก Wharton เป็นผู้ตั้งคำนี้

เราอาจค่อย ๆ เปลี่ยนไปโดยไม่ทันสังเกต ครั้งแรกอ่านละเอียด ครั้งต่อมาแค่อ่านคร่าว ๆ สุดท้ายดูแค่หัวข้อแล้วกดยอมรับ พอมีคนถามว่าทำไมถึงเขียนแบบนี้ กลับตอบไม่ได้ แม้จะให้ agent ช่วยอธิบายก็ตาม

โค้ดยังดูดีและ test ยังผ่านได้ ทั้งที่คนในทีมไม่เข้าใจระบบแล้ว Addy เชื่อมเรื่องนี้กับ [[comprehension-debt|หนี้ความเข้าใจ]] คือช่องว่างระหว่างสิ่งที่ระบบทำจริงกับสิ่งที่คนในทีมรู้

อย่างไรก็ดี เขาไม่ได้คาดหวังให้ใครจำ codebase ใหญ่ ๆ ได้ทั้งหมด เขาเล่าว่าทีม Claude Code จะค่อยทำความเข้าใจส่วนที่ต้องแก้เมื่อถึงเวลา โดยให้ Claude ช่วยอธิบาย สิ่งสำคัญจึงอยู่ที่เรารู้หรือไม่ว่าตรงไหนยังไม่เข้าใจ และพอจำเป็น เรากลับไปทำความเข้าใจจนตอบคำถามได้จริงหรือเปล่า

งานที่เลือกผิดแล้วไม่เสียหายมาก อาจยกให้ AI ตัดสินใจได้เลย Addy ยกตัวอย่างการเลือกโรงแรมจากตัวเลือกที่คะแนนใกล้กัน แต่ถ้าเป็นเรื่องว่าจะสร้างอะไร การเปลี่ยนแปลงจะกระทบผู้ใช้คนไหน หรือพร้อมปล่อยให้คนใช้หรือยัง คนที่รับผิดชอบต้องอธิบายเหตุผลได้เอง

## หกคำถามที่ช่วยให้เราไม่เชื่อตามทันที

ก่อนอ่านคำตอบที่ดูน่าเชื่อ Addy จะลองตั้งความเห็นของตัวเองไว้ก่อน แล้วใช้คำถามเหล่านี้ตรวจว่าตัวเองยังคิดตามอยู่หรือไม่

1. **ก่อนถาม เราคิดไว้ว่าอย่างไร?** เดาผิดได้ แต่ควรมีสมมติฐานของตัวเองก่อนเห็นคำตอบ ถ้าไม่รู้จะเริ่มตรงไหน ให้ agent ช่วยชี้เรื่องที่เราอาจยังไม่ได้นึกถึง
2. **กำลังให้มันช่วยคิด หรือให้มันคิดแทน?** ทำได้ทั้งคู่ ขอแค่รู้ตัวว่าเลือกแบบไหน
3. **คำตอบนี้จะผิดได้ในกรณีไหน?** อย่าหยุดที่ถาม model ว่ามั่นใจแค่ไหน ลองหาวิธีทดสอบกรณีนั้นจริง ๆ
4. **ได้ฟังคนที่คิดต่างหรือยัง?** เรื่องที่ยังถกเถียงกันได้ เขาจะให้หลาย model ลองเสนอข้อโต้แย้ง แล้วค่อยตัดสินใจเอง
5. **ถ้าคนที่ต้องดูแลงานนี้ต่อมาถาม เรากล้ายืนยันไหม?** ต้องเข้าใจพอจะอธิบายและรับผิดชอบสิ่งที่ส่งให้เขา
6. **ช่วงนี้ไม่ได้ฝึกอะไรเองแล้วบ้าง?** บางทักษะอาจปล่อยได้ แต่ควรเป็นเรื่องที่เราตัดสินใจแล้ว

## Test ผ่าน แล้วมันตรวจอะไรไปบ้าง

ถ้าเตรียมวิธีตรวจให้ agent มันก็แก้โค้ด รัน test อ่านผล แล้วแก้ซ้ำเองได้ เช่น ให้ลองใช้งานแอปตั้งแต่ต้นจนจบ หรือเขียน test ตรวจเงื่อนไขที่ระบบต้องรักษาไว้ วิธีนี้ช่วยให้คนไม่ต้องนั่งตามทุกขั้น แต่ยังต้องดูว่าวิธีตรวจนั้นจับปัญหาที่เราห่วงได้จริงหรือไม่

สมมติว่า agent เข้าใจ requirement ผิด แล้วเขียนทั้งโค้ดและ test ตามความเข้าใจเดียวกัน Test ก็ผ่านได้ทั้งที่ฟีเจอร์ยังผิดอยู่ ไฟเขียวจึงไม่ได้บอกว่าทุกอย่างถูกต้อง

> When a check goes green, ask what it proved. Then ask what it didn't.

พอ test ผ่าน ลองถามว่า “มันยืนยันเรื่องอะไรให้เราแล้วบ้าง แล้วมีอะไรที่ยังไม่ได้ตรวจ?”

Addy แนะนำให้ตกลงเกณฑ์ผ่านตั้งแต่ก่อนเริ่มงาน จะได้ไม่มาหาเหตุผลเข้าข้างผลงานทีหลัง หลักฐานอาจเป็นผล test ภาพหน้าจอ หรือ log ที่แสดงว่าโปรแกรมทำอะไรไป เมื่อ agent บอกว่าเสร็จ ให้อ่านก่อนว่ามันรันคำสั่งอะไรและได้ผลอย่างไร แล้วค่อยอ่านสรุปของมัน

เขายังเสนอให้ใช้ subagent ที่เริ่มด้วย context ใหม่มาตรวจงานอีกที และถามท้ายงานว่ายังตกหล่นอะไรหรือไม่ ส่วนงานที่ไม่ใช่โค้ดก็ต้องย้อนดูหลักฐานเหมือนกัน เช่น สุ่มอ่านบันทึกสัมภาษณ์ลูกค้าต้นฉบับ หรือเช็กวิธีคำนวณตัวเลขที่ใช้ประกอบข้อเสนอ

**สิ่งที่ช่วยได้:** เราไม่ต้องไล่ทำงานซ้ำทุกขั้น แต่ต้องรู้ว่าผลตรวจที่เห็นตอบข้อสงสัยของเราได้แค่ไหน

## อย่าอ่านแค่ว่าแก้อะไร ให้ดูด้วยว่ามันเลือกอะไรแทนเรา

ระหว่างทำงาน agent ตัดสินใจเรื่องเล็ก ๆ แทนเราหลายอย่าง เช่น จะใช้ค่าไหนเป็น default จะตัดอะไรออกจากงาน หรือจะตีความอย่างไรเมื่อ requirement สองข้อขัดกัน สรุปท้ายงานที่บอกว่า “ทำเสร็จแล้ว” อาจไม่เล่าเรื่องพวกนี้เลย

เวลา [[agentic-code-review|review โค้ดจาก agent]] จึงควรขอให้มันบอกด้วยว่าตัดสินใจอะไรไปและตั้งสมมติฐานอะไรไว้ จากนั้นลองเลือกโค้ดบางบรรทัดมาอธิบายเอง ถ้าเป็นเอกสาร ให้ปิดแล้วลองเล่าว่าใจความคืออะไร จะให้ agent ออกคำถามทดสอบความเข้าใจท้ายงานก็ได้

Agent ยังช่วยคัด PR และชี้จุดที่น่าตรวจเป็นพิเศษได้ แต่ถ้างานที่มันทำเสร็จกองเร็วกว่าที่เราอ่านทัน การเปิด agent เพิ่มก็ยิ่งเพิ่มภาระ นี่คือ [[orchestration-tax|ปัญหาที่ agent ผลิตงานได้มากกว่าคนจะตรวจไหว]] ตามที่ Addy เคยเขียนไว้ ทางออกคือตรวจอัตโนมัติให้ดีขึ้นจนเหลืองานที่ต้องใช้คนดูน้อยลง หรือชะลอการผลิตงานลงก่อน

**สิ่งที่ช่วยได้:** เรามีเวลาเข้าใจเรื่องสำคัญพอจะรับรองงานที่ส่งต่อ ไม่ใช่กดผ่านเพียงเพราะงานค้างเยอะ

## ถ้าเราเองยังไม่ชัด agent ก็อาจเดาจนงานดูเสร็จ

เมื่อก่อน ถ้าสั่งงานคลุมเครือ คนรับงานอาจถามกลับจนเรารู้ตัวว่ายังคิดไม่จบ แต่ agent อาจเติมสิ่งที่เรายังไม่ได้บอก แล้วส่งงานที่หน้าตาเรียบร้อยกลับมา ทั้งที่เป้าหมาย ข้อจำกัด และเหตุผลเบื้องหลังยังไม่เคยคุยกันให้ชัด Addy เรียกปัญหานี้ว่า **intent debt** และเห็นว่าเจ้าของงานต้องเป็นคนคลี่คลายเอง

เขาแนะนำให้เขียนคำอธิบายงานด้วยคำของตัวเองก่อน ว่าทำให้ใครใช้ อะไรไม่อยู่ในงานนี้ และจะรู้ได้อย่างไรว่างานเสร็จ ถ้าสั่งแก้สองรอบแล้วยังไม่ตรงใจ ให้กลับมาเขียนคำขอใหม่ หรือให้ agent ถามเราเพื่อช่วยหาว่าตรงไหนยังไม่ชัด

ข้อมูลที่ป้อนให้ agent ก็สำคัญ ถ้าส่งแต่บทสรุปต่อกันไปเรื่อย ๆ agent ตัวที่สามอาจไม่เคยอ่านต้นฉบับเลย ส่วนงานที่ดูเรียบร้อยก็ไม่ได้แปลว่าดีพอ ต้องมีมาตรฐานของเราเองว่างานแบบไหนถึงจะยอมส่งออกไปในชื่อเรา

ถ้างานไม่ผ่าน ให้จดด้วยว่าไม่ผ่านเพราะอะไร แล้วนำไปเพิ่มในคำแนะนำที่ agent อ่าน หรือทำเป็น hook และ test ที่คอยตรวจรอบต่อไป วิธีนี้ตรงกับ [[harness-ratchet|การนำข้อผิดพลาดมาปรับระบบให้ไม่พลาดซ้ำ]]

**สิ่งที่ช่วยได้:** แต่ละรอบไม่ได้จบแค่แก้งานให้ผ่าน เรายังได้คำขอและเกณฑ์ตรวจที่ชัดขึ้นสำหรับงานครั้งหน้า

## ต่อให้ model เก่งกว่าเรา ใครจะเป็นคนรับผิดชอบ

Addy ยอมรับว่าในอนาคต model อาจจับข้อผิดพลาดได้ดีกว่าคนในหลายเรื่อง แต่ยังต้องมีคนตัดสินใจว่าจะเชื่อมันแค่ไหน จะสร้างอะไร ทำไปทำไม และยอมแลกอะไรบ้าง เพราะผลของงานยังตกกับคนจริง ๆ

เขาอ้างงานวิจัยของ Anthropic ที่เรียกปัญหาหนึ่งว่า **paradox of supervision**: ทักษะเขียนโค้ดที่ต้องใช้ตรวจงาน Claude อาจเป็นทักษะเดียวกับที่เราเริ่มทำไม่คล่อง เพราะปล่อยให้ AI ทำแทนอยู่ตลอด เรื่องนี้เชื่อมกับ [[skill-atrophy|ทักษะที่เสื่อมลงเมื่อไม่ได้ฝึก]]

วิธีที่เขาเสนอคือ สัปดาห์ละครั้งลองทำงานสำคัญบางอย่างโดยไม่ใช้ agent เดือนละครั้งลองจดว่าเลิกทำอะไรเองไปแล้ว และมีอะไรที่ยังอยากทำเป็นอยู่ ถ้าเจอเรื่องที่ไม่เข้าใจ ก็ใช้เวลาเรียนให้เข้าใจ ส่วนเวลาตรวจงานต้องนับเป็นเวลาทำงานและเผื่อไว้จริง ๆ ไม่ใช่หวังว่าจะหาเวลาว่างมาทำได้เอง

ไม่จำเป็นต้องทำตามทุกข้อ ให้เลือกสิ่งที่เข้ากับงานของเรา จุดสำคัญคือเรายกงานให้ AI ทำได้ แต่คนที่รับผิดชอบสิ่งที่ส่งออกไปยังเป็นเรา
