# Critical Thinking When Agents Do the Work / เมื่อ agent ทำงานแทน เรายังต้องคิดอะไรเอง

[[addy-osmani|Addy Osmani]] ผู้เขียนเรื่อง software engineering และการใช้ AI agent เสนอว่า ยิ่ง model ตอบได้เร็วและดูถูกต้อง คนยิ่งต้องตั้งใจจัดเวลาให้การคิดวิเคราะห์เอง เขายังสนับสนุนการใช้ agent เต็มที่ แต่ไม่อยากให้ความสะดวกทำให้เรารับงานไปโดยไม่มีความเห็นของตัวเอง

## จากฝากงาน ไปถึงฝากความคิด

Addy แบ่งการใช้ AI เป็นสามระดับ เพื่อให้คนสังเกตว่าตัวเองกำลังส่งต่ออะไรอยู่

- **Cognitive offloading:** ให้ AI ทำงาน แต่เรายังตรวจและรับผิดชอบผล
- **Deferral:** เอาคำตอบของ AI ไปเป็นข้อมูลตั้งต้นรอบต่อไป โดยเลิกมองว่ามันเป็นสมมติฐานที่อาจผิด
- **[[cognitive-surrender|Cognitive surrender]]:** รับคำตอบมาเป็นความคิดของตัวเองจนไม่รู้สึกว่าต้องตรวจ ผู้เขียนให้เครดิตคำนี้กับ Steven Shaw และ Gideon Nave จาก Wharton

การไหลลงมาทีละขั้นอาจไม่รู้ตัว รอบแรกอ่านละเอียด รอบถัดไปอ่านคร่าว ๆ แล้วเหลือแค่ดูโครง พอมีคนถามถึงรายละเอียดกลับอธิบายไม่ได้ นี่ทำให้ [[comprehension-debt|หนี้ความเข้าใจ]] สะสม แม้โค้ดจะดูเรียบร้อยและ test ผ่าน

แต่เราไม่จำเป็นต้องจำระบบใหญ่ทั้งก้อน ผู้เขียนเล่าว่าทีม Claude Code สร้างความเข้าใจเฉพาะส่วนกลับมาเมื่อต้องใช้ สิ่งสำคัญคือรู้ว่าตัวเองยังไม่เข้าใจตรงไหน และสร้างความเข้าใจกลับมาได้จริง งานที่ผิดแล้วเสียหายน้อยอาจฝากให้ AI ตัดสินใจทั้งหมดได้ ส่วนเรื่องที่จะสร้างอะไร กระทบใคร หรือปลอดภัยพอจะส่งให้ผู้ใช้หรือยัง ต้องเก็บเหตุผลไว้กับคนรับผิดชอบ

**ได้อะไร:** แยกการลดภาระงานออกจากการเลิกตรวจ โดยไม่ตั้งข้อเรียกร้องว่าคนต้องจำทุกบรรทัด

## คำถามก่อนและหลังใช้ agent

ผู้เขียนใช้คำถามเหล่านี้ดึงตัวเองกลับมาคิด แทนการอ่านคำตอบแล้วเห็นด้วยทันที

1. ก่อนถาม เราคิดว่าคำตอบน่าจะเป็นอะไร แม้เป็นการเดาก็ควรตั้งสมมติฐานไว้ก่อน ถ้ายังไม่รู้จุดตั้งต้น ให้ agent ช่วยหาสิ่งที่เรามองข้าม
2. เราขอให้มันช่วยคิด หรือยกงานคิดให้มัน รู้ตัวหรือไม่ว่ากำลังทำแบบไหน
3. ต้องเกิดเงื่อนไขอะไรคำตอบนี้ถึงจะผิด แล้วเราจะทดสอบเงื่อนไขนั้นอย่างไร
4. ได้ฟังข้อโต้แย้งจากมุมอื่นหรือยัง อาจให้หลาย model ลองค้าน แล้วคนตัดสินเอง
5. กล้ายืนยันผลนี้ต่อหน้าคนที่ต้องดูแลมันต่อหรือไม่
6. มีทักษะอะไรที่เราเลิกฝึก และยอมให้ทักษะนั้นหายไปจริงหรือเปล่า

## ทำให้การตรวจเป็นส่วนหนึ่งของงาน

Agent สามารถแก้โค้ด รัน test อ่านผล และแก้ซ้ำเองได้ ถ้ามีวิธีตรวจที่ชัด เช่น end-to-end test, property test หรือการใช้งานแอปจริง แต่คนยังต้องตัดสินว่า test นั้นพิสูจน์สิ่งที่สำคัญหรือไม่ ถ้า implementation กับ test เข้าใจผิดเรื่องเดียวกัน ทั้งคู่ก็ผ่านพร้อมกันได้

> When a check goes green, ask what it proved. Then ask what it didn't.

พอผลตรวจผ่าน ให้ถามว่ามันพิสูจน์อะไร และยังไม่ได้พิสูจน์อะไร

กำหนดก่อนเริ่มว่าอะไรนับว่างานผ่าน และขอหลักฐานที่จับต้องได้ เช่น ผลคำสั่ง screenshot หรือ trace เวลา agent แจ้งว่าเสร็จ ให้อ่านคำสั่งที่มันรันกับผลลัพธ์ก่อนอ่านสรุป ผู้เขียนเสนอให้ agent ตรวจงานตัวเองด้วย context ใหม่ แล้วถามหาสิ่งที่ตกหล่นอีกครั้งด้วย แต่ไม่ได้ถือว่าการตรวจแบบนี้แทนคนได้ทุกกรณี

นอกงานเขียนโค้ดก็ใช้หลักเดียวกัน ถ้า agent สรุปสัมภาษณ์ลูกค้า ให้ย้อนดูเอกสารต้นทางบางชิ้น ถ้าข้อเสนอพึ่งตัวเลขตัวหนึ่ง ให้ตรวจการคำนวณตัวนั้น

**ผลคือ:** การมีเครื่องมือตรวจไม่พอ ต้องรู้ด้วยว่าหลักฐานนั้นครอบคลุมอะไร

## อ่านการตัดสินใจที่ซ่อนอยู่ในงาน

[[agentic-code-review|การ review โค้ดจาก agent]] ต้องดูทั้ง diff และเรื่องที่ agent เลือกแทนเรา เช่น default ขอบเขตที่ตัดออก หรือ requirement ที่ตีความใหม่ ขอให้มันแจกแจงการตัดสินใจและสมมติฐาน แล้วลองอธิบายโค้ดบางบรรทัดด้วยตัวเอง ถ้าเป็นเอกสาร ให้ปิดแล้วลองเขียนใจความจากความจำ การให้ agent ทำแบบทดสอบท้ายงานเป็นอีกวิธีเช็กว่าเราเข้าใจจริง

Agent ช่วยคัด PR และชี้จุดเสี่ยงได้ แต่ถ้างานเสร็จสะสมเร็วกว่าที่เราตรวจทัน การเปิด session เพิ่มจะไม่แก้ [[orchestration-tax|ช่องว่างระหว่างงานที่ผลิตกับงานที่คนรับรองไหว]] ต้องเพิ่มคุณภาพของการตรวจอัตโนมัติหรือลดปริมาณงาน

**ได้อะไร:** ใช้ความสนใจกับจุดที่ต้องตัดสินจริง และไม่ปล่อยให้ความเร็วของ agent ลดมาตรฐานการรับงาน

## คุณภาพเริ่มตั้งแต่คำขอ

คนยังต้องคิดทั้งก่อนเริ่มและหลังงานเสร็จ ถ้าคำขอคลุมเครือ agent อาจเติมช่องว่างให้จนงานดูเสร็จ ทั้งที่เป้าหมายยังไม่ชัด ผู้เขียนเรียกเป้าหมาย ข้อจำกัด และเหตุผลที่ซ่อนอยู่แบบนี้ว่า **intent debt** คนเจ้าของงานต้องทำให้ชัดเอง

เขาเสนอให้เขียน brief ด้วยคำของตัวเอง ระบุคนที่จะใช้ สิ่งที่ไม่ทำ และเกณฑ์ว่าเสร็จเมื่อไร ถ้าแก้ prompt สองรอบแล้วยังไม่ถึงเป้า ให้กลับมาเขียนใหม่ หรือให้ agent สัมภาษณ์เพื่อหาจุดที่ไม่ชัด ระวังการส่งสรุปต่อกันหลาย agent จนตัวหลังไม่ได้อ่านต้นฉบับ

ส่วนงานที่ไม่ผ่านมาตรฐาน ให้จดเหตุผลไว้ใน config, hook หรือ test แนวทางนี้เชื่อมกับ [[harness-ratchet|การเปลี่ยนข้อผิดพลาดให้เป็นกติกาป้องกันรอบหน้า]]

## Model เก่งขึ้นก็ยังต้องมีคนรับผิดชอบ

ผู้เขียนยอมรับว่า model อาจตรวจข้อผิดพลาดได้ดีกว่าคนมากขึ้น แต่การตัดสินว่าจะเชื่อมันแค่ไหน และอะไรคุ้มค่าที่จะสร้าง ยังเป็นงานของคน เขาอ้างงานวิจัยของ Anthropic เรื่อง **paradox of supervision** ว่าการกำกับ Claude ต้องใช้ทักษะเขียนโค้ดที่อาจถดถอยเพราะพึ่ง AI มากไป ตรงนี้เชื่อมกับ [[skill-atrophy|ทักษะที่เสื่อมเมื่อไม่ได้ใช้]]

ข้อเสนอสำหรับชีวิตประจำวันคือ ฝึกงานสำคัญโดยไม่ใช้ agent สัปดาห์ละครั้ง ทบทวนทุกเดือนว่าเลิกทำอะไรเองไปบ้าง และจัดเวลาตรวจงานไว้จริง ๆ แทนการถือว่าเป็นงานฟรี ผู้เขียนไม่ได้กำหนดให้ทุกคนต้องทำทุกข้อ แต่ให้เลือกสิ่งที่เข้ากับงานและทักษะที่ยังอยากรักษา
