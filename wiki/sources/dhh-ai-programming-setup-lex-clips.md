# DHH's New Setup for Programming with AI / ชุดเครื่องมือเมื่อโปรแกรมเมอร์คุม agent หลายตัว

[[dhh|David Heinemeier Hansson (DHH)]] ผู้สร้าง Ruby on Rails เล่าให้ Lex Fridman ฟังว่าเขาย้ายจากการเขียน code ทีละปัญหา มาคุม AI agent หลายงานพร้อมกันผ่าน terminal ความสนุกกลับมาเมื่อเขามีเรื่องให้ตัดสินใจระหว่างรอ agent แต่พอเพิ่มเครื่องจนคุมราว 16 งานพร้อมกัน เขาก็เริ่มชนขีดจำกัดของตัวเอง

อีกตอนของบทสัมภาษณ์เดียวกันสรุปไว้ที่ [[dhh-strategies-programming-with-ai-agents-lex-clips|Strategies for Programming with AI Agents]] ซึ่งพูดถึงวิธีสั่งงานและตรวจงาน agent การรีดขนาด installer ของ [[omarchy|Omarchy]] และการใช้เสียงป้อนโจทย์

หน้านี้สรุป **transcript ช่วง 0:03–12:20 ที่ผู้ใช้ส่งมา** ของคลิปจากช่อง Lex Clips ไม่ใช่บทสรุปทั้งตอน วันที่ ingest ไม่ใช่วันเผยแพร่คลิป ตัวเลขและคำประเมินประสิทธิภาพเป็นประสบการณ์ที่ DHH เล่า ไม่ใช่ผล benchmark

## จาก TextMate ไปสู่ flow แบบหลายงาน (0:14–2:47)

DHH ใช้ TextMate ซึ่งเป็น editor สำหรับเขียน code มาเกือบ 20 ปีตั้งแต่ราวปี 2005 จนย้ายไป Linux แล้วต้องเปลี่ยนเครื่องมือ เขายังอยากเรียกงานที่ทำร่วมกับ agent ว่า programming แม้รูปแบบงานจะเปลี่ยนไปแล้ว

เมื่อก่อน flow คือจดจ่อกับปัญหาเดียวจนแก้จบ แต่ agent ใช้เวลาทำงานนานกว่าการตอบสนองทันทีจากแป้นพิมพ์ ขณะเดียวกันก็ผลิต code เร็วกว่าคน พอเปิดแค่ตัวเดียว เขาจึงรู้สึกนั่งรอและไม่ค่อยมีประโยชน์

พอเปิดหลายตัว เขามีงานตัดสินใจต่อเนื่อง เช่น ช่วยเลือกทิศเมื่อ agent ติดคำถาม หรือส่งโจทย์ถัดไปหลังงานเสร็จ เขาเรียกประสบการณ์นี้ว่า flow เช่นกัน แม้จะต่างจากการจดจ่อกับ code ชิ้นเดียว

ผลคือ การคุมงานหลายชิ้นช่วยเติมช่วงรอสำหรับ DHH แต่ยังต้องแยกความรู้สึกทำงานต่อเนื่องออกจากคุณภาพของงานที่ส่งมอบ ดู [[creative-ownership|Creative Ownership]] แนวคิดเรื่องความรู้สึกว่าเราได้ใส่ความคิดและการตัดสินใจของตัวเองลงในงาน

## Terminal และ Herdr ช่วยตามงาน (2:47–4:26)

DHH เริ่มจาก tmux ซึ่งแบ่ง terminal เป็นหลาย pane หรือพื้นที่ทำงานย่อย พอมีหลาย agent บนหลายเครื่อง เขาเปลี่ยนไปใช้ [[herdr|Herdr]] เครื่องมือจัดการ agent session ใน terminal โดยมี Herdr แยกอยู่บนแต่ละเครื่อง

จุดที่เขาใช้คือสถานะว่ายังทำงานอยู่หรือไม่ และเสียงแจ้งเตือนเมื่อ agent เสร็จหรือต้องการคำตอบจากคน เขายังชอบ TUI (terminal user interface) และไม่ได้ย้ายไปใช้แอปแบบ GUI เป็นหน้าหลัก

ผลคือ คนรู้จังหวะที่ต้องกลับไปตัดสินใจได้ง่ายขึ้น แต่เสียงแจ้งเตือนไม่ได้ทำให้คนตัดสินใจได้เร็วขึ้นเอง ตรงนี้เชื่อมกับ [[attention-bottleneck|Attention Bottleneck]] ซึ่งมองว่าสมาธิและเวลาของคนเป็นข้อจำกัดของงาน agent

## เพิ่มเครื่องผ่าน Comet และ Tailscale (4:26–6:20)

DHH อยากใช้ mini PC เก่าที่มีอยู่ จึงต่อ GL.iNet Comet ซึ่งเป็น KVM สำหรับดูหน้าจอและควบคุมเครื่องจากระยะไกลผ่านสาย HDMI กับ USB แล้วใช้ [[tailscale|Tailscale]] เชื่อมอุปกรณ์เป็นเครือข่ายส่วนตัวที่เรียกว่า tailnet

เขาเล่าว่าเข้าถึงเครื่องในออฟฟิศ Malibu และ Copenhagen จากโทรศัพท์ได้ และการตั้งค่านี้ทำให้เพิ่มเครื่องมารัน agent ง่ายขึ้น จึงต่อคอมพิวเตอร์ในตู้เพิ่มสี่เครื่อง

ผลคือ เขานำเครื่องที่มีอยู่กลับมาใช้กับงานหลาย session ได้ คลิปไม่ได้ระบุว่า model ประมวลผลในเครื่องเหล่านี้ หรือใช้บริการ model ภายนอก และไม่ได้อธิบายการแยก repo กับวิธีรวมงานจากแต่ละเครื่อง

## ราว 16 งานพร้อมกันคือขีดจำกัดของเขา (6:20–8:05)

DHH ประมาณว่าใช้ 4–5 เครื่อง เครื่องละราว 3 agent รวมแล้วคุมได้ประมาณ 16 “threads” ตัวเลขทั้งหมดเป็นการกะระหว่างเล่า ไม่ใช่รายการเครื่องที่นับได้พอดี และคำว่า threads ในที่นี้หมายถึงงาน agent ที่เขาตามอยู่ ไม่ใช่จำนวน CPU thread

> “the faster the agents run, of course, the fewer threads I can run.”
>
> ยิ่ง agent ทำงานเร็ว เขายิ่งตามงานพร้อมกันได้น้อยลง (6:20–6:43)

เขาเปรียบเทียบว่าจากเดิมเขียนได้ราว 20–30 บรรทัดต่อชั่วโมง ตอนนี้บางช่วงได้หลายร้อยบรรทัด แต่หยุดย้ำเองว่าจำนวนบรรทัดเป็น metric ที่ไม่ดี มันบอกปริมาณ output ไม่ได้บอกว่างานดีหรือสร้างอะไรที่มีคุณค่า

ผลคือ 16 เป็นขีดจำกัดส่วนตัว ณ จังหวะการทำงานที่เขาเล่า ไม่ใช่จำนวน agent ที่ทุกคนควรเปิด นี่เป็นตัวอย่างของ [[orchestration-tax|Orchestration Tax]] ต้นทุนที่คนต้องจ่ายเพื่อตรวจและปิดงานที่ agent หลายตัวสร้างขึ้น

## Neovim ยังมีค่าเพราะดูไฟล์นอก diff ได้ (8:05–9:11)

DHH ยังใช้ Neovim ซึ่งเป็น editor ใน terminal แต่ใช้เปิดดูโครงสร้างโปรเจกต์มากกว่าเขียน code และเรียก lazygit เพื่อดูการเปลี่ยนแปลงใน Git เขาคิดว่าหน้า pull request ของ GitHub อาจเหมาะกับงานนี้ถ้าแสดงผลเร็วกว่านี้

เขาชอบหน้าตา diff ของ Hunk ซึ่งแสดงส่วน code ที่เปลี่ยน แต่เวลา review งาน agent เขาอยากเปิดดูไฟล์อื่นที่ยังไม่ได้แก้ด้วย เช่น เปลี่ยนไฟล์นี้แล้วมีอีกไฟล์ที่ควรแก้ตามหรือไม่ จึงยังใช้ Neovim เพื่อดูบริบทรอบงาน

ผลคือ หน้าจอ review ควรพาคนจาก diff ไปสำรวจ code ที่เกี่ยวข้องได้ ข้อสังเกตนี้เสริม [[agentic-code-review|Agentic Code Review]] ซึ่งจัดวิธีตรวจงานตามความเสี่ยง โดยเพิ่มคำถามว่า agent ลืมแก้ส่วนไหนนอก diff หรือเปล่า

## Linux และ config file ทำให้ agent ตั้งค่าเครื่องได้ง่ายในประสบการณ์ของ DHH (9:11–12:20)

DHH ชอบ Unix philosophy ที่มีเครื่องมือเล็ก ๆ เรียกผ่าน CLI หรือ command-line interface และตั้งค่าผ่านไฟล์ เขามองว่าสิ่งที่เคยทำให้ Linux ใช้ยากกลับเอื้อต่อ agent เพราะสั่งเครื่องมือและแก้ config ได้ตรง ๆ

เขาชม Homebrew ซึ่งช่วยติดตั้งซอฟต์แวร์บน Mac แต่เล่าว่าการตั้งค่า Raycast และ key binding บางส่วนยังต้องผ่าน GUI Lex แย้งว่ามีวิธีอ้อม ส่วน DHH เห็นว่าวิธีที่ลองยังไม่ดีพอ **เก็บข้อโต้แย้งทั้งสองไว้:** คลิปนี้ไม่ได้ทดสอบทุกวิธีหรือทุกเวอร์ชัน จึงยังสรุปไม่ได้ว่า macOS ทำ automation เหล่านี้ไม่ได้เลย

Lex ใช้ Windows เพราะต้องทำงานกับ Adobe Premiere และเคยใช้ Windows Subsystem for Linux (WSL) เพื่อรัน Linux ภายใน Windows ทั้งคู่มองว่าขอบเขตแบบ sandbox ขัดกับการให้ agent ตั้งค่าเครื่องได้ทั่วถึง นี่เป็นความต้องการของ workflow ที่เล่า ไม่ใช่ผลเปรียบเทียบระบบปฏิบัติการหรือหลักฐานว่า WSL ใช้กับ agent ไม่ได้

ผลคือ คำถามที่นำไปใช้ต่อได้คือเครื่องมือเปิดให้ agent อ่าน แก้ และนำ config กลับไปใช้ซ้ำได้แค่ไหน ดู [[agent-experience|Agent Experience (AX)]] ซึ่งว่าด้วยสิ่งที่ช่วยหรือขวาง agent ระหว่างทำงาน

- [[orchestration-tax]] เตือนว่าความยุ่งอาจไม่เท่ากับได้งาน ขณะที่ DHH บอกว่าการมีเรื่องตัดสินใจต่อเนื่องช่วยให้เกิด flow ทั้งสองด้านอยู่ร่วมกันได้ คลิปไม่มีข้อมูลคุณภาพหลัง merge หรือภาระระยะยาวพอจะบอกว่า flow แบบนี้ยั่งยืนแค่ไหน

- ประเด็นค้างของ setup นี้คือวิธีแยกงานที่ชนกัน การตรวจและรวมงานจากหลายเครื่อง ค่าใช้จ่าย และภาระจาก notification คลิปไม่ได้ลงรายละเอียดเหล่านี้
